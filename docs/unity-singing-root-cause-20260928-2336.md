# 最新歌唱测试评估与局部替换方案（2026-09-28 23:36 快照）

结论：这次歌唱失败同时包含接口错误、录音指代状态错误、现有声学裁切方法的能力限制。继续叠加提示词、重试和独立审核无法解决整个链路。建议把下一阶段限定为歌唱子系统的局部替换：固定录音与演唱轮次身份，维护当前演唱任务，直接分析音频的说话/歌唱时间段；复用现有 SVC 与播放，普通对话、移动和跟随暂不扩展修改。

本次仅评估、复制留存证据、隔离复现和对现有 ASR 服务做两次只读音频分析。没有修改生产代码，没有安装模型、部署或重启服务，没有播放音频或操作角色。

## 两个工程错误

### 裁剪定位词的三套约束不一致

`RecordingSingingBoundary.cs` 的 JSON schema 只设置最大长度；C# 编译器要求 `keep.Trim().Length >= 4`；Python endpoint 归一化后要求至少 3 字符。本场“初めて”恰好 3 字符。模型已经给出真实的中文排除句与日语保留定位词，却被隐藏的 C# 约束拒绝。

这属于内部契约错误。直接把错误解释成“用户还没说明白”是不合适的。单独调整长度虽然能让请求往下走，但下面的真实音频复测证明它不能保证最终切成功。

### 同一来源因时间坐标的 JSON 往返被判为变更

`RecordingBoundarySource.MatchesProposal` 对 `material.Description` 经 JSON 解析后的 segments 与原始 `TranscriptSegments` 使用 `JToken.DeepEquals`。原坐标来自 C# `float`，JSON 解析后变成 `double`。例如同一 6.35 秒坐标：

- 原 `Single` 转为 double：`6.3499999046325684`；
- 写成 JSON `6.35` 再解析：`6.35`；
- `DeepEquals` 为 false。

在 `boundary-roundtrip/` 中直接编译当前生产 `RecordingBoundarySource.cs`，使用项目自带 Newtonsoft.Json DLL，在 key、revision=0、ready 状态、PCM hash、两侧原文、范围全部相同时，真实 `MatchesProposal` 返回 false；仅统一坐标的表示后对照返回 true。`result.json`、编译源码与 DLL hash 均已留存。c15 实际分轨就有 6.35、11.87 等坐标。

这提供了足以解释 c18 的具体生产方法复现；原现场日志没有记录是哪一个内部比较失败。不能仅凭错误名断言用户录音真的变了。此前“0 与 pending 版本名错配”的初步猜测已排除为本例已证实根因：c15 当时已确认，revision0 本身可能正确。

修复应统一源身份与坐标契约：固定 PCM hash、录音 ID、数值版本和整数采样坐标；ASR 文本修订单独编号。不要将经 JSON 重建的整份浮点文本证据是否逐值相等，作为 PCM 是否还是同一来源的判据。

## 下一阶段应替换的范围

### 1. 当前演唱任务与素材身份成为稳定状态

建立同一歌唱任务下的演唱轮次（take），分别保存：当前目标、当前录音、被重唱替代的旧录音、用户关于范围的修订、待处理/已准备/已播放状态。新的普通讲话、催促和解释不能自行替换演唱素材；明确请求第一段时仍可选择旧 take。

“我重唱第二段”→实际新录音→“轮到你唱了”应更新同一任务。“把它唱出来”从该任务取得当前素材，不能每次依靠全库存和上次成功播放重新猜。角色是否愿意唱仍由角色决策；一旦采纳回唱意图，结构化操作必须绑定这份 take，公开承诺和实际任务应一致。

### 2. 音频分段成为独立能力

输入原 PCM，输出带时间坐标的 speech/singing/uncertain 区间与证据；语义分类使用 ASR 辅助理解唱前说明、实际歌声和唱后请求，声学模型负责时间上的说/唱判断。静音、音高、ASR 都可以作辅助，不能让某一个启发式成为唯一可执行条件。

保留中文讲话加日文歌唱的本场上下文提示，但不能把语言规则写成全局判断：中文也能唱歌，日文也能说话。支持多个歌声区间和区间之间的讲话，不只支持一次 lead 或 tail 修改。

Jev 类文本判断器可以做意图、任务切换与分段语义检查；ASR 文本本身无法恢复同一句话究竟是说出来还是唱出来及其精确音频边界。增加 Jev 不能替代这个音频能力。

模型方面先建立能逐帧输出的音频事件检测基线，再看真实录音是否需要场景微调。PANNs 官方实现已有 sound-event-detection / framewise 输出，可作为候选基线；这不是证明它在本项目上一定够准，也没有在本次安装或测速。[作者仓库](https://github.com/qiuqiangkong/panns_inference/blob/master/README.md)

### 3. 模型选择已有片段，执行器统一校验

歌唱模型接口以 `take_id`、已生成的 `segment_id`、操作（准备/回唱/排除/替换）为核心。常规回唱不再要求模型逐字抄歌词来获得音频处理许可；歌词识别错字不应阻止保留旋律的原音频转换。

源 hash、版本、范围、用户取消和播放顺序仍由程序检查。已有明确任务时，收敛重复的全库存模型检索、重新选材和再次解释意图；有歧义时才进行额外选择。当前增量倾听可以提前计算候选分段/转换准备，最终收音和意图确认后才提交播放。并行准备不能继续复用陈旧的素材许可。

## 验收方式必须改变

下一批先使用现有真实录音与实际对话序列，在 Unity 外完成可重复验收，再接现场。并行推进来源/状态契约和音频分段候选实验，而不是先把一个新模型串入正式链路。

至少需要覆盖：纯唱、唱前说话、唱后说话、两侧都有讲话、没有明显静音、多次说唱交替、重新唱第二段、随后多轮解释/催促、明确改选旧段、取消；保留一组未用于调阈值的录音。

分别衡量：

1. 正确素材选取率：本场 c17 必须绑定重唱后的第二段，独审通过或 WAV 能播放都不是正确选材的替代指标。
2. 讲话漏入、歌声被截、边界误差：须听辨原音与切片并保留标注；模型候选不是标准答案。
3. 成功完成率与拒绝率：不能靠全部拒绝换取零漏读。
4. 实际首歌声延迟及 P50/P95：拆开录音结束、分段就绪、SVC、播放；不能用模型 API 耗时冒充用户等待。
5. 同一源完整序列化与多轮状态回放：必须覆盖本次真实小数坐标、录音修订、短指代和重唱，不能只测试手工整数秒或协议合法性。

前一批的接口/状态回归通过，只证明其覆盖范围内的约束成立，不证明混合音频被正确裁切。本次也暴露了新增边界证据的序列化测试缺口。后续必须把真实音频和真实选材序列纳入发布验收，避免仍让用户逐轮发现下一层问题。
