# 公开语音、任务保持与收尾准备：2026-09-15 交付

本批承接 [最新 Play 评估](scene-play-assessment-20260915.md)，集中修复公开台词误播、两段回唱在追问中缩水，以及倾听准备迟迟无法使用的问题。原项目已有修改均保留，未编辑正式房间场景。实际模型验证沿用同一份远端 Qwen，没有加载第二个语言模型。

## 已落地的行为

**公开台词必须有明确边界。** 普通回复、工具回复、执行反馈及纠错统一使用声明了语言和阶段的 `<say>` 台词。裸 `lang code=ja`、`speech mode=after_action`、未标注的推理内容不能进入公开语音；静默工具动作仍受原执行审核管理。合法台词可以边生成边送入语音，后续格式失败会隔离剩余内容和工具指令。已送达回调的前缀单独记录为事实，并明确“不代表已播放”，避免纠错时假定前缀从未输出。

**未完成的歌唱任务有独立的持续目标。** 追问清理本轮可执行提案，但保留已审核的片段身份、顺序、范围、版本与成功条件。默认续接不能悄悄将“两段”缩成“第二段”；明确修改或取消仍由模型判断，并经过原话证据和独立审核。素材版本由真实清单绑定，实际播放完成后再核对全目标，旧回调不能完成新任务，完成的任务不会自动重复。

原日志还有一个重要细节：首次两段提案被语音阶段错误剥除，尚未成功登记。因此只保存已批准任务还不够；本批另保留最近六次真实用户输入作为恢复证据，让后续审核能看到原要求。它们不是程序识别出来的指令，语义仍由模型解释。

**倾听准备提前调度、精简请求并增加可追溯记录。** 原文稳定 0.20 秒后可以准备，支持两个字符以上的短句；每个采集/输入代际最多三次普通准备，取消也占用预算。请求只携带角色设定、少量参考和完整当前原文，不再附带全部旧工具及视觉上下文。没有提高 256 token 预算，没有增加第二个模型或额外并发通道。最终 ASR、原文修订、新声音、静音尾部覆盖、取消代际检查均保留。

## 本批没有启用的分支

**提前语义闭合默认只记录观察结果，不自动结束录音。** 实际 Qwen 测试发现：改进提示词后完整短句可闭合，但“我刚才说错了，不要”仍被当成完整否定指令，连续两次误判。最终 ASR 和声学静音只能证明输入覆盖与停顿，不能纠正这一语义误判。

因此 `m_EnablePreparedBoundaryReuse` 默认关闭；满足机械复用条件时记录 `shadow-hit`，仍返回未采用，正式收尾继续原来的专用复核。只有隔离回归显式启用实验分支来检查撤销保护。没有把该反例删除、改成期望成功，或调置信度门槛迎合样本。

这意味着本批**没有证明实际首音达到 1.5 秒**，也没有完成“收尾准备在真实语音中可靠命中”的验收。后续应先用录音停顿与续说轨迹评估边界模型，不能再只以提高 `hit` 数为目标。

## 验证与限制

验证集中在既有 `unity-naturalness-validation` 隔离项目。实际模型审核使用合成任务；普通对话延迟采用最终文本注入和真实 Qwen/TTS，不能替代麦克风 Play。

- 公开边界纯回归 18,830 项；本次冻结日志的原始反例分包回放 6,834 项。
- 真实生产 ChatQW 到本机 HTTP 测试端的 17 个请求通过 78 项检查，覆盖正常台词、工具、静默、裸协议、推理及合法前缀后格式失败。该项不涉及扬声器或真实模型。
- 持续歌唱目标最初独立 Unity 回归 188 项通过；补充恢复案例后，最终组合运行通过 201 项。它验证程序状态、身份与回调，不能单独证明模型会正确规划或实际歌声内容正确。
- 最终组合回归 `controlled-final` 退出码 0、无 C# 编译错误：包含 113 项准备状态/调度检查、42 项真实 ChatSample 接口检查（含默认只观察、独立复核与实验撤销），以及首答分流、播放交接和前述公开边界回放。
- 新 15 例真实 Qwen 审核，原始判定 13/15；经生产审核与提交逻辑回放，有效判定 14/15。三个新增的目标恢复/保持/明确修改案例全部通过。剩余合法音高调整被模型误拒，仍可能造成额外纠错等待；未发现测试反例被错误批准。完整批次保留 `passed=false`。
- 提前收尾的最终 8 例真实模型测试为 7/8；未完成纠错误判仍在，不能计为通过。生产默认旁路记录正是基于这项失败。

原始测试失败、响应、请求 SHA 和程序审核记录均保存在 [证据目录](../Server/ARDY/runtime/response-reliability-20260915/)。其中 `controlled-r1/r2` 是集成接口或旧断言修复前失败；`controlled-r3/r4/r5` 是保留的模型语义失败；`ordinary-r1` 在正式对话测量前因 ARDY 未启动而失败，不计入有效延迟样本。

### 真实 Qwen＋TTS 延迟

最终代码与提示词的四条最终文本输入均完成语音播放，`ordinary-final` 退出码 0。测试在本机静音，记录 AudioSource 的实际 PCM 推进，不是人工听感，也不包含麦克风、ASR 和收尾耗时。

| 输入 | 实际通道 | 文本提交→首个正式 PCM |
|---|---|---:|
| 晚上好，今天只聊聊天。 | 普通 | 3.10 s |
| 整理房间累了，怎样休息？ | 工具流程，最终未提交动作 | 8.89 s |
| 更正：不要放音乐，只聊天。 | 普通 | 2.46 s |
| 暂时不唱歌，你喜欢怎样的晚上？ | 普通 | 2.77 s |

三条普通通道中位数 **2.77 秒**；全部四条 **2.94 秒**。首音本身可能仍是问候，不能等同于实质答案已经完整送达。最慢一条普通生活建议被模型选择交回工具流程，大上下文输入计算约 4.57 秒；这条没有从统计中排除。首句 TTS 等待约 0.57–1.28 秒，仍占据明显成本。

较早的 `ordinary-r2` 四条首音为 8.45 / 8.41 / 4.68 / 3.14 秒，还出现中文台词声明 `ja` 和过长回答。随后统一了两处遗漏的格式示例，最终批次语言声明与可见文字一致，但仍有回复偏长和普通问题走工具流程的问题。两批存在模型采样、提示词和缓存/热机状态差异，**不是证明性能提升的因果 A/B**；不只保留较快一批。见 [完整延迟摘要](../Server/ARDY/runtime/response-reliability-20260915/latency-summary.json)。

本批核心收益是明确输出与任务状态边界；1.5 秒首音目标仍未达到。下一批应拆开解决无必要的工具分流、大上下文输入计算和首句 TTS，并单独验收真实停顿/续说的收口可靠性。

最终 35 个相关文件记录在 [源码清单](../Server/ARDY/runtime/response-reliability-20260915/delivery-source-manifest.json)，其中 32 个相对本轮基线有变化（含元文件和回归工具）；全部 Assets 文件与隔离验证副本 SHA 一致。

## 下一次 Play

使用平时的启动脚本并重新进入 Play，让 Unity 加载新代码和提示词。重点复查三组行为：普通聊天的完整首句、句中停顿后追加否定、两段录音按顺序回唱并在失败追问后保持两段。再验证明确改成只唱第二段和取消，确认持续任务没有阻碍用户改主意。

本次验证启动了共享 Qwen、TTS 和 ARDY，并保持可用；完整语音/回唱所需其他服务仍请由原启动脚本统一检查启动。

新日志会区分 `[Semantic EOU/Listening]` 请求生命周期、`[Listening/Wire]` 返回和 `[Semantic EOU/Prepared] shadow-hit/miss`。评估仍以实际停说至有效台词播放为准，同时保留无回复轮次；不把内部准备耗时或首 token 当作首音。
