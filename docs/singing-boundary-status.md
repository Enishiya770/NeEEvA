# 歌唱链路与语音延迟：现状与遗留问题

分支 `feat/memory-graph-urge-model`，截至 2026-08-16。

这份文档记的是**判据是怎么来的、哪些数是拟合出来的、哪些假设已经被证伪、
哪些路径还没验证过**。代码注释里有各处的局部推导，这里只放全局结论——
改这块之前先看这份，尤其是"已排除"那几节，省得重复走死路。

涵盖两条线：歌唱边界／模态判定（前半），以及回哼转换与首次发声延迟（后半）。

## 这条链路在做什么

用户对着麦克风说话，其中可能夹着演唱。系统要回答三个问题：

1. **这一轮里有没有真正的演唱？**（模态判定）
2. **唱的是哪一段？**（边界／岛检测）
3. **该不该把它用角色声线唱回去？**（回哼门控）

三个判据来源：**声学**（音高稳定度、周期性、持续音）、**文字**（整轮转写 + 分段歌词，交给 LLM）、
**流式**（说话途中的起唱点与"心里话"）。它们互相取交集而不是任一方独断——因为每一路都有
**已经实测到的**系统性盲区，见下。

## 已建立的基线

2026-08-10 第一次有了人工真值：用户逐段听音频，标出 29 段素材的起唱／唱完时刻。
标注是通过一个临时生成的本地网页做的（每段一个播放器、两个打点按钮，进度存
localStorage）——它刻意**不显示**转写、当前岛边界和 `singing_probability`，
否则拿到的就不是独立真值。页面生成在 `band_dumps/` 里，那个目录已 gitignore，
所以仓库里没有；要重做一批标注就重新生成一个。

在此之前每次改动都只能靠单个案例判断好坏，这也是之前几次改动来回撤销的原因。

对 27 段单段演唱素材：

```
起点误差 中位 0.13s  最大 2.22s  超过 1s 的 1/27
终点误差 中位 0.10s  最大 1.85s  超过 1s 的 1/27
```

## 判据的由来与脆弱处

### 岛的取舍下限 0.60（最需要留意的一个数）

候选岛的取舍用「把这座岛单独当成一段音频跑一次 `analyze()` 得到的概率」，
下限 `_ISLAND_PROB_FLOOR = 0.60`。

- 稳定窗口是 **[0.59, 0.61]**（三点结果完全一致），但 0.58 和 0.62 都退化到 4/27。
  **窗口只有约 ±0.015 宽，且是 27 段素材拟合出来的。**
- 27 段里 21 段对阈值完全不敏感，全部波动来自 6 段边缘素材。
- crepe 本身不确定：连跑 4 次有 1 次某段翻面（1/27 变 2/27）。生产环境里同一段音频
  在流式期间会被反复分析、服务端对周期性做了跨次平均，方差比离线单次小。

**它替换掉的旧判据（候选窗均分 + 下限 0.80）失败得很彻底**，两类分数完全交错：

```
说话  0.786   0.805   0.809
唱歌  0.733   0.778
```

三次反例出现之后才换判据。所以：**再遇到反例，应该换判据，而不是继续挪这个数。**

### 起点仲裁只看"岛比流式晚多少"

原判据是 `Abs(岛 − 流式) <= 1.0`。绝对差是错的方向——岛比流式**早**时 `min()` 本来就
选岛，保护根本不起作用；只有岛比流式**晚**才是"可能跳到后半句"。而且 1.0 是硬悬崖：
实测差 1.06s（只超 0.06）就退回保护值，1.81 秒说话被当成歌唱了回去。

现在容忍度 1.75s，**依据很薄**，只有两个方向相反的实测点：晚 1.06s→岛正确、
晚 2.50s→岛错误。取在两者之间。

### 模态判定的提示词已经到顶

拿 28 段真值 + 29 条真说话转写量了**五种写法**，漏判（真唱了判成说）死死卡在 **6/28**：

| 写法 | 总准确率 | 漏判 | 误判 |
|---|---|---|---|
| 现版 | 82% | 6/28 | 4/29 |
| 加段落点明"混合轮" | **56%** | 24/28 | 1/29 |
| 改问"有没有歌词" | 81% | 11/28 | 0/29 |
| 现版 + 一句"混合情况答 singing" | 84% | 6/28 | 3/29 |
| 现版 + "通篇"二字 | 82% | 7/28 | 3/29 |

漏判清一色是【评价上一次 + 宣布要唱哪首 + 唱】这种形态，其中多条唱的是《演员》——
歌词字面就是「说话的方式简单点」，**文字这一侧对这首歌没有信息量**。

判据推不动，所以改的是**代价**：软降级不再静默丢弃，改为让角色出声追问。

### 分段歌词只在整轮未收录时才附加

整轮 ASR 在长的混合录音上只转得出开头：实测 26.7s 的【说话+日文演唱+说话】只转出前
6.5 秒，演唱和尾巴全丢。所以演唱段和尾部各做一次独立转写。

附加分段歌词有个陷阱：整轮已经包含同样的字时重复贴一遍会把模型推向 singing，
削弱文字否决权。用去重字符重合率 <60% 作闸，并在提示里写明"引用不算唱"——
12 样本上从 9/12 提到 11/12。

### 尾部撤回判定的提示词也是量出来的

第一版只问"是不是在作废"，12 样本 10/12，**两个错都是假阳**：
「这首歌叫演员，是薛之谦的。」和「那我们下一首换一个吧。」都被判成作废。
假阳是不能出的方向——它会静默吞掉一段本该回哼的演唱。补上反例清单
（评价／介绍歌曲／让你跟唱／换下一首都不算作废）并写死"拿不准答 keep"后 12/12、假阳 0。

## 回哼转换的设备选择（8/10 重新量过）

`RVC_GPU_MIN_FREE_MIB` 决定回哼的音色转换走 GPU 还是 CPU。这道闸只是"别做无谓
尝试"——真正的安全网是 `attempts = [True, False]`，CUDA OOM 会自动退回 CPU。

原值 1500，而全套服务起来之后实测空闲显存只有 **1109~1122 MiB**，于是每一次回哼
都被推到 CPU，CUDA 那条路从来没被试过。降到 1000 之后，同一段 20.4s 素材实测：

```
CUDA  8.70 / 8.71 / 8.82s   (n=3)
CPU  12.53 / 12.73s         (n=2)
```

省约 3.9s（31%），4/4 成功，转换期间空闲显存降到 157~198 MiB。

两个要知道的点：

- **首次启用的第一次转换要 33.13s**（CUDA 内核自动调优）。那份缓存落在磁盘上，
  重启服务不再付——上面第三个 8.70s 就是服务重启后的第一次，验证过。
- **实际空闲显存随负载在 1100~2200 MiB 之间浮动**，1000 是按低点定的。余量很薄：
  如果日志里看到转换耗时突然回到 12s 以上，那是 OOM 退回了 CPU，属于预期行为。

一个曾经引用错的数：日志里"CPU 中位 16.9s"是不同素材、不同负载下量的，同源对照
其实是 12.6s。**跨素材比时间没有意义，要比就用同一段。**

## 首次发声延迟：已排除的与未决的

目标是首次发声平均 2 秒内。8/10 一场 12 次发声：中位 1.36s、均值 1.72s、
最大 3.52s，**超过 2 秒的有 4 次**。慢的几次全都卡在 LLM 首 token
（2.68 / 2.86 / 3.50s），不是 ASR 也不是 TTS。

**已排除**（都做了对照，别再重复）：

- *上下文太长*——不成立，而且是反的。首 token 对上下文长度非单调：
  历史 3453 字符时 3.50s，8580 字符时 0.67s。后半程上下文大得多反而快 5 倍。
- *辅助 LLM 调用（模态判定/撤回判定）顶掉主对话缓存*——串行对照下主对话
  0.50s → 0.58s，钉不钉槽都一样。
- *视觉/感知帧*——最慢的三轮带 0 个感知帧，最快的两轮带 2 个，没有相关性。

**未决，且最可疑**：投机预生成的并发抢占。依据是 `AbortPrewarmIfRunning` 的注释里
已经实测记录过同一形状的问题——

> 这里放弃的只是**等待**，服务端不会跟着停…被 Abort 的预热照样跑完
> （prompt eval 19865.85ms / 8927 token），那笔 GPU 时间照付。
> 用户若在这期间开口，真实请求会排在预热后面，首轮反而更慢——实测首 token 10.48s。

`CancelEphemeralMsg`（投机草稿）也只是 `Abort()` 客户端等待，形状完全一样。
草稿的 prompt 是主对话的前缀、相似度极高，会去竞争主对话那个槽。

合成测试**没能定论**：单次复现出 4.26s 尖峰（基准 0.5s），但再跑 9 次没复现——
因为测试每轮复用同一对 prompt，第一轮后两个槽各自缓存好，进入了真实对话永远
达不到的稳态。**要定论只能看 llama-server 自己的控制台**，它每次请求都打槽位号和
复用/重算的 token 数；Unity 侧看不到这个。下次跑测试时留一份那个窗口的输出。

## 边界细化为什么不能无条件开

同样是为了守住 2 秒目标：

- 逐岛细化只在**整段 prob ≥ 0.40 且时长 ≥ 8s** 时做。它让 `analyze()` 从 0.89s 涨到
  1.53s（每座岛 0.24s、一轮约 3.6 座），普通对话轮不能付这个钱。
  需要纠正边界的素材全部 ≥ 11.8s，短句要么整段说要么整段唱，旧判据本来就对。
- 尾部转写（约 0.25s）和撤回判定（约 0.5s）只在歌唱轮发生，而且**与歌声转换并行**——
  转换本身要 12～20 秒（SVC 跑在 CPU 上），完全藏得住。

## 曲库：唱了就记，取用时必须允许"不确定"（8/16）

这一节是 8/12～8/16 连着几场实测打出来的结论，也是下一阶段的主线。

### 两次唱错，根因都不是"选错了"，是没有可选项

- **8/11**：上下文里只出现过一个歌曲 ID（`f8dc749c3350`）。用户说"跟我一起唱"时她
  想执行歌唱动作，手上就这一个 ID，于是把它又放了一遍。
- **8/16**：用户要"把刚才唱的两段合起来"。`mode=practice` 因为练唱会话是 0 段而连败两次，
  她改走 `mode=continue`，靠 `combinedMatch=0.69`／`lyricsMatch=0.00` 命中了 `5ffa03166fd5`——
  这条 entry 里同时挂着《演员》和 Lemon 两首歌，于是 Lemon 被唱了 12.88 秒。
  0.69 在实测分布里就是噪声水平（跨组中位 0.675，见下）。

`song_search.py` 里**没有任何"歧义／多个候选／需要确认"的概念**：`song_sing id=X` 一律直接解析、
直接唱。她不是选错，是结构上没有"我不太确定是哪首"这条路。

### 唱了就记（已改）

`CommitRecentSingingToPracticeSession` 原本绑着 `armed`——用户没先说过"跟着我唱"就一段都不记。
8/16 实测用户直接唱了两段、都判高区、都进了持久曲库，练唱会话却是 0 段。已改为
`confirmedSinging` 就记。分工是：**唱了就进记忆；要不要复现、要不要和别的段结合，
由用户和她商量决定**。感知帧已经在报「练唱会话: 已记录 N 段」，判断权在她。

未解决的副作用：练唱会话只在"约定跟唱"和 Agent Loop 启动时清空（上限 16 段）。
一场里唱了五首不同的歌，`mode=practice` 会把五首连起来。先不加自动清空——
等看到她真的把不相干的歌连起来，再决定边界怎么划。

### 身份数据：一半已经在了

40 条曲库的字段填充率：

| 字段 | 有值 | 说明 |
|---|---|---|
| 时间 | 58/58 | 每次录音各带 `created_at`，粒度到每一遍 |
| 旋律 | 58/58 | `pitch_contour_midi` + timeline |
| 歌词 | 38/40 | 8/12 用落盘 wav 重转写补的；剩 2 条 wav 已丢失 |
| 歌名 | 12/40 | |
| 作者 | 6/40 | |
| `reason` | 58/58 | **她当时自己的话**，从没被读出来过 |

`reason` 是"描述／她的感受"的现成雏形（如「主人が歌ってくれた Lemon の次の段落を正式に保存」），
一直在逐次积累，但回忆和演唱都不看它。

### 旋律相似度撑不起任何门槛（已量，别再试）

拿曲库里已知的重复组量过两轮（第一轮分组有 bug，同一首被拆成多组，已修正后重跑）：

```
melody_similarity   组内(同一首) 中位 0.701   跨组(不同首) 中位 0.675    213 对 vs 490 对
  阈值 0.70   认出 107/213   误认 189/490
  阈值 0.80   认出   9/213   误认   2/490   ← 干净但几乎无用
```

样本量翻五倍后分布依然重合。原因在实现：轮廓重采样到 220 点再取差分，**时长和调性都被抹掉，
只剩起伏形状**，而人声旋律的起伏形状天生相似。最容易误认的一对是 `Lemon × 雪下的那么深`
（0.799，一首日文一首中文），比 39 对真同歌里的 16 对还高。

所以本机回忆**刻意不设置信度门槛**：`SongSearchEngine.recall()` 只按分数取前几名，
连同歌词和上次听到的时间一起交给她判断——**能分辨这几条的是歌词语义，不是旋律数字**。
唱歌轮的 `[演唱片段; …]` 末尾会自动带上这个候选列表。

### 下一步的形状

```
写入   唱了就记（已改）+ 她自己的描述/感受（reason 已在写，再补歌名/作者/印象）
取用   用户提到某首歌
```

## 遗留问题

### 未验证的代码路径

- **软降级追问**只真正跑通过一次（角色问出「刚才那段，其实是在唱吗？」）。但那次她紧接着
  拿用户的说话去查曲库、然后自己说「还是算了吧」把话收回去了。修正文案（素材就在手边、
  不要查曲库、不要在用户回答前自我否定）是在那之后才加的，**尚未验证**。
- **撤回中止**从未真正触发。三次判定都是"保留"且都判对了，中止那条分支零实测。

### 已知无解的形态

- **故意用歌唱般的声调说话**。用户做过 5 次这类对抗探测，挡住 3～4 次，全靠文字判据。
  漏掉的那次转写是「没有问题，你这次处理的很棒…I love you I love you.」——
  「I love you」作为一句著名歌词被说出口，声学（0.63）、模态判定、乃至让 LLM
  抄写唱词，三方**一致地判错**。
  当天为此试过六组新判据（比例问法四种、跨度分歧、唱词位置），无一可用：
  比例问法跟着提示词的暗示走而不是跟着内容走（暗示"没唱"→ 全答 none；暗示"唱了"→
  目标案例答 most）；跨度分歧**方向是反的**；位置差 89% vs 全判对的基线 84%，
  且只在 2/3 的轮次上给得出意见。
  结论：为这一个对抗样本去换约 25% 正常轮次多问一句，不划算。**期望行为是保留素材但先问**。
- **乐句头尾被切掉**（前一轮记录，仍未解决）：一句的头尾比中间安静，分数偏低而被切掉，
  表现为「前半句没了」或「尾音突然断」。需要基于能量包络连续性的新特征，是新工作不是调参。
- **日文跟唱歌词听不清**（中文正常）：mora 与音符的对齐问题，中文对齐器在日文上的切分率
  0.22～1.00 不稳定，要根治需要日语强制对齐器。SVC 为默认后端时这条走不到。

### 环境限制

SVC 跑在 CPU 上（每次转换 12～20 秒），因为空闲显存 519 MiB 低于
`RVC_GPU_MIN_FREE_MIB=1500`。显存已到极限，不能靠加并发解决。

## 复现与调试

- **落盘**：整段 prob 落在 0.25～0.70 时，`trim_to_speech` 之后的音频与当时的分析
  会存进 `Server/SenseVoice/band_dumps/`（已 gitignore，仅供离线定阈值）。
  按音频内容 sha1 去重——流式期间同一轮会被反复分析，去重前 20 个文件只对应 9 个轮次。
  开关 `NEEEVA_BAND_DUMP=0`。
- **岛日志**：`[Island] … floor=0.60 runs=[0.90-3.30/0.81(p0.55)* …]`。
  斜杠前是旧的窗口均分、括号里 `p` 是新判据（该岛单独分析的概率），
  `*` = 过了长度/窗口数、`+` = 过了分数下限。**这一行是定位边界问题的第一入口**。
  注意它打在**服务端控制台**，不在 Unity 的 Editor.log 里。
- **诊断切片**：把某一段按秒切开送回 `/asr`，能直接看出哪一截是说话、哪一截是唱——
  这两天每一次定位边界靠的都是它，而不是声学分数。但要记得它自己也会触发落盘，
  用完清掉。
