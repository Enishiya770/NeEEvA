# 停止控制、录音回唱交接与等待链修复

本次针对 `docs/log-review-20260926-1352.md` 中最新对话的具体故障，同时审查能够重叠的工作。验收区分纯协议、模型含义判断、Unity 控制器实际受理和真实服务/听感，不把任一层通过当成整条链路通过。

## 已实现的运行时变化

- **晚审核后的歌唱启动交接。** Agent 和 Direct review 共用 `QueueReviewedSingingRequest`。审批已消费后，完整 `QueueHumBack` 仍负责来源、范围、版本与渲染器检查；只有新受理队列才补一次 `TryBeginPendingHumBack`。因此 `<silent/>` 先排空、审核后到的顺序不会留下永久 pending。已开始准备的生产者不会再次启动。
- **独立的当前任务停止控制。** FastLoop v2 将 `task_control`、当前任务 ID 和用户原文证据与回应路线分开。只有有效的当前任务停止提案才再调用一个 32-token 上限的独立分类器，只看完整当前输入与身体任务事实。两份判断都确认结束该任务，且独立分类与捕获的真实任务类型匹配，才允许取消；具体跟随/移动类型由后者规范化。运行时捕获 bridge/controller/avatar/environment/user、任务和操作版本，停止前再次核对，通过 `StopForTaskIfCurrent` 取消同一个任务。控制器已确认停止才生成成功回执；新任务会让未播放的旧回执失效。后续回唱继续保留完整当前输入和控制结果。
- **录音回唱直接路由。** `recording_singing` 直接进入已有录音 IR；角色草稿被 ActorIntent 认定为 `other_action/replan/task=other` 时，先选择技能再进入 Room。非回唱结果仍保留必要的空间规划。此路由不选择音频片段、范围，也不代替来源/演唱审批。
- **灯具完成回执。** 对实际 `performed` / `already-satisfied`，action/entity、完成图像身份、绑定和实时设备读回全部一致后，用中文、日语或英语的短事实回执，省去后置自由说明和复核两次模型调用。状态更改、取消、换代后，播放前校验会撤销旧回执。
- **填充语等待后的再次校验。** 缓冲音频从队列取出后可能等待 filler；在这段异步等待后、调用 `AudioSource.Play` 前再次检查事实，避免等待期间失效的停止/设备回执被播放。

## 等待与并行

| 路径 | 本次处理 | 依赖边界 |
|---|---|---|
| 角色草稿 → 意图判定与首句 PCM | 保留现有并行准备 | 判定/实际任务受理前不公开准备音频 |
| 正文 TTS → 已批准歌唱转换 | 保留并验证两者重叠 | 歌唱声音等正文排空；取消或新轮撤销旧生产者 |
| 录音回唱 → Room → 额外路由 | 明确回唱直接进入录音 IR | 原素材、范围、审批与执行校验仍串行依赖 |
| 灯具执行 → 自由说明 → 复核 → TTS | 成功事实直接进入 TTS | 瞬时开关不为等待意向语音而延后 |
| 同一个 Qwen 对象上的多个规划请求 | 不盲目并发 | 多种请求共享取消/所有权槽；直接并发可能互相取消 |

详细代码证据和未实施候选见 `work/control-async-repair-20260926/async-dependency-audit.md`。本次减少的是依赖链中的无必要工作，并修正真正的异步完成交接；不把所有调用包进 `Task.Run`，Unity 对象操作仍在主线程。

上一轮日志中，灯具完成到首音约还有 **9.7–9.9 秒**，其中正式说明与复核各约 **4.3–4.4 秒**；此处被替换的正是这两个阶段。歌唱那轮审批本身约 **13.91 秒**，之后排队未启动而超时；本次启动修复不代表审批耗时已经下降。所有这些都是修改前的日志分解，不是修改后真人对话的延迟实测。
