## 修复优先级应围绕普通闲聊调整

1. **分离原话、观测和指令。** 路由依据纯用户话语、独立的声学/语义证据和真实未完成事项；程序写的“歌唱概率/歌词/曲库”说明不能触发歌唱话题。完整歌词、分段时序和旋律观测仍保留给角色理解，不能为提速删除证据。
2. **恢复普通闲聊的增量发声。** 没有依赖动作校验的普通回复，首个可说片段就进入 TTS。歌唱承诺的校验范围需要明确，不能由“详细技能已加载”一项决定整轮等待。
3. **减少闲聊每轮重算的输入。** 让稳定规则复用，整理 `PrepareUserTurn` 与 `BuildFormalObservationContext` 重复构造的感知信息；普通闲聊使用精简且完整的当前状态，需要处理歌唱任务时才展开详细规则。保留角色感知能力与尚未完成事项。
4. **检查实际缓存复用和首块长度。** 后续验收要同时记录每次输入重算 token、prefill、正文首段、TTS 及停说至正式首音。缓存/检查点参数调整须先验证，不直接承诺某个固定加速倍数。

优先验证场景应为：刚启动后的问候、连续闲聊、唱歌后改聊天气、关闭再开启实时模式后的闲聊。目标是恢复以往普通对话的响应水平，而不是把一声填充音记作已经回答，也不要求用户为了闲聊先关闭唱歌能力。

完整远端日志复制曾被自动审批拒绝，理由是日志可能包含敏感内容。已采用更小范围的远端只读数值提取完成上述核查；无须复制整份日志，也没有因此阻塞本次评估。
