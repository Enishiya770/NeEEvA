# 2026-09-11 说话转唱歌的感知核查

后续状态：已按本文与复读复盘实施修复，详见 [修复及验证记录](2026-09-11-speech-song-loop-fix.md)。下文保留当时日志结论。

核查结论：录音、两句歌词和音高分析都有取得；正式角色输入却被一条跑题的流式判断降级为“本轮是普通说话”，并失去了本轮的旋律音符、音域及旋律检索摘要。歌词仍通过完整转写和素材事实到达正式请求。角色随后把用户已经完成的演唱转成了自己的演唱任务，独立目标审核也没有纠正这个意图错误。

用户已明确澄清：这一轮没有要求角色回唱。因此本案应按“用户先说话，再自己演唱；角色理解并回应这段已发生的输入”评估。不能把 ASR 的破碎标点或角色自行提交的目标反过来当成用户要求。

本次只读核查日志与实现，更新评估文档；没有修改运行代码、启动场景、播放录音或将真实对话发送给模型回放。

## 1. 听觉采集取得了什么

|---|---|---|
| 0–5.63 秒 | 中文口语开头 | ASR 把“我”断成独立短句，行为主语需要结合后续演唱理解 |
| 5.63–10.67 秒 | 第一句日语歌词 | 声学候选为 singing；歌词是识别结果，可能有误字 |
| 10.67–16.46 秒 | 第二句日语歌词 | 聚合类型为 uncertain，素材尾部另标 speech；均不能推断没有歌声 |

原始内容录音长 16.46 秒，服务端最终 `singing_p=0.666`，音高稳定度 0.65；输入摘要中确实出现音域 `A#2～B3` 和音符序列。干净播放候选为 5.24 秒，扩展候选为 11.03 秒，见 [音频与音高留存](../../Logs/repetition-20260911/004910/Editor.normalized.log:4846)。

因此没有证据支持“话音一结束就把后面的歌整段丢掉”。保守的 clean 边界只覆盖第一句，确实会影响后续播放范围，但第二句的录音和转写仍保留着，不能等同于角色没有收到第二句文字。

| [5034](../../Logs/repetition-20260911/004910/Editor.normalized.log:5034) | 最终文本与草稿一致度仅 0.10，草稿被放弃；但降级已执行 |

时区内容与 [上一轮正式回答](../../Logs/repetition-20260911/004910/Editor.normalized.log:3675) 对应。流式请求确实携带对话历史，当前歌词 partial 又已退化；这支持“草稿受上一话题影响”的判断。日志没有证明是网络旧响应串入或服务端缓存错误，不应把它说成已经确认的传输故障。

实现中有三处确定的问题：

1. [草稿接收与否决](../../Assets/AIChatTookit/Scripts/Chat/ChatSample.cs:2321) 只验证请求代次、当前模式及源转写与当前 partial 的连续度，再依据模型填写的 `mode_confidence` 给予否决权；没有验证判断理由是否对应当前录音区间。转写连续度为 1.00 不能证明回答的时区话题与当前音频相关。
2. [融合函数](../../Assets/AIChatTookit/Scripts/Chat/ChatSample.cs:2496) 在流式 singing 和 speech 同时成立时归为语义 uncertain；声学为 singing 时又返回 AcousticSinging。[最终回调](../../Assets/AIChatTookit/Scripts/Chat/ChatSample.cs:3473) 没有将这种流式内部矛盾识别为需要完整证据复核的冲突，却继续单独应用 speech veto。这使“保留过唱歌判断”与“最新 speech 判断”能够同时存在，最后仍被整轮降级。
3. [最终证据覆盖函数](../../Assets/AIChatTookit/Scripts/Chat/ChatSample.cs:2553) 依赖 `m_FinalModeVerdict == "singing"`；当前实现只初始化/清空该字段，没有设置 singing 的路径。另一个后台语义复核写入的是不同字段 `m_SemanticVerdict`。而 [草稿最终一致度检查](../../Assets/AIChatTookit/Scripts/Chat/ChatSample.cs:3912) 排在降级之后，不能撤销已经写入的错误输入结论。

## 3. 歌词与旋律到达角色的情况不同

### 歌词：正式请求里确实有

[5195 行](../../Logs/repetition-20260911/004910/Editor.normalized.log:5195) 的实际请求诊断包含完整 `recording_transcript`，其中有中文开头和两句日语歌词，同时保留 `acoustic_mode=singing singing_p=0.666`。

该诊断读取的是 [最终序列化 JSON](../../Assets/AIChatTookit/Scripts/LLM/QW/ChatQW.cs:96)，在 [发送相同字节前](../../Assets/AIChatTookit/Scripts/LLM/QW/ChatQW.cs:2073) 调用；并非只记录了 ASR 上游结果。日志的 `messages=11` 与统计项的 8 分别计算附加上下文后的消息数和历史数，不表示最后三条输入被丢弃。

此外，[5455 行](../../Logs/repetition-20260911/004910/Editor.normalized.log:5455) 的正式模型输出在 `sing_goal.expected` 引用了第一句歌词。这证明至少有歌词信息参与了动作生成，但不能证明模型理解了两句歌词的内容，或正确理解了“用户刚才已唱过”。外放只剩一串“明白、现在唱、准备好了”，没有体现对用户演唱的回应。

### 旋律：程序提取了，但本轮的音符摘要在降级时被去掉

[降级分支](../../Assets/AIChatTookit/Scripts/Chat/ChatSample.cs:3554) 把 `LastIsSinging` 设为 false 后重新构造 `_msg`，开头成为：

> 实时倾听辅助判断：本轮是普通说话；此前约定不构成本轮声学事实，不得复述、转换或保存本轮音频

[BuildLastPerceivedText](../../Assets/AIChatTookit/Scripts/TTS&&STT/SenseVoice/SenseVoiceSpeechToText.cs:2435) 此时保留完整文字及分轨，却不再调用 `BuildSingingPrefix`。本轮的音域、音符序列及旋律检索候选都在该前缀中。因此 ASR 日志打印过这些数据，不等于正式角色请求仍携带它们。

隔离候选的 [素材事实](../../Assets/AIChatTookit/Scripts/Chat/ChatSample.SingingProtocol.cs:354) 仍给出概率、稳定度、旋律岛时长和边界窗口类型，没有补回本轮的音符序列。底层音高数据及录音未因此全部销毁；损失发生在呈现给角色的摘要层。

当前 [正式请求格式](../../Assets/AIChatTookit/Scripts/LLM/QW/ChatQW.cs:273) 只包含文本和图片，没有音频输入。因此角色在这条链路中依靠声学系统提供的文字事实理解声音，不能把底层存在音频/MIDI 解释成角色直接听到了原始旋律。本轮只能确认它得到了一些歌唱特征，不能确认它获得并理解了具体旋律。

正式输入最终同时含有“本轮是普通说话”的断言、两句歌词、按时间排序的 singing 候选及 `acoustic_mode=singing`。把相互冲突的结论交给模型，并不等于完成了感知融合。

## 4. 为什么又进入了回唱与复读

用户没有要求回唱。角色仍在 [5455 行](../../Logs/repetition-20260911/004910/Editor.normalized.log:5455) 自行登记 perform 目标并宣布要唱；[5503 行](../../Logs/repetition-20260911/004910/Editor.normalized.log:5503) 将它记为 `autonomous=false`。[5851 行](../../Logs/repetition-20260911/004910/Editor.normalized.log:5851) 的独立审核又说目标与“用户请求”一致。

这说明意图核对也没有达到预期：角色的演唱提议被当成了用户尚未完成的要求。`autonomous` 的 [当前赋值](../../Assets/AIChatTookit/Scripts/Chat/ChatSample.SingingGoal.cs:139) 依赖工作状态，并不单独证明用户提出过该目标。

程序随后在错误任务上推进，才触发上一份报告记录的五次相近承诺与相同失败。播放校验失败仍是复读循环的直接触发条件；本次发现则解释了更前面的两个缺口：用户演唱未获得恰当回应，以及为什么一开始就生成了不符合用户意图的任务。不能断言只修一个分类分支就能同时消除全部问题。

## 修复应覆盖的方向

1. **保留感知事实，独立约束动作。** 是否允许自动跟唱、是否存在可播放版本，可以阻止动作；不能据此删除已取得的歌词、音高摘要，或断言整轮没有歌唱。未定的模态作为候选并列呈现。
2. **按录音区间记录判断。** 每条 partial 判断带本次录音身份、覆盖范围和来源；说话转唱歌、歌词大幅回滚、草稿跑题或最终完整证据到达时，旧结论应失去整轮否决权。最终一致度检查应在任何降级副作用之前；不用一条全局 speech/singing 标签代替整轮时序。
3. **分开用户做了什么、用户要求角色做什么、角色自己想做什么。** 本例允许自然回应用户已经完成的演唱，也允许角色在既定自主边界内作自己的选择；不能把自行提出的回唱追记成用户任务，进而触发持续追赶与反复承诺。
4. **验收完整行为。** 覆盖“说话→两句歌→无回唱要求”、后半段流式文本回滚、最后草稿错回旧话题、speech/singing 证据同时存在、尾句被标 uncertain、无歌词哼唱，以及纯说话被声学误报。检查正式请求是否保留歌词和旋律事实，角色是否理解已发生的演唱，并确认不会凭空建立用户回唱任务；另行覆盖确实要求回唱及角色自主发起的情况。

这需要与 [复读复盘](2026-09-11-singing-repetition-review.md) 中的无进展收口、等待审核与失败计数修复一起考虑，不能只给模型追加一句“不要复读”或“记得听歌词”。
