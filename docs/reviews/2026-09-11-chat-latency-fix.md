# 2026-09-11 闲聊延迟修复与验证

依据 [闲聊延迟核查报告](2026-09-11-chat-latency-regression.md) 的优先级实施。此次修改围绕普通对话的输入与增量发声，没有调整远端模型缓存参数，也没有删除歌词、旋律或未完成事项来换取更小的请求。

## 已修改的行为

1. **技能路由区分原话与观测。** 普通语音前缀里的“歌唱概率、歌词、旋律、曲库”不再触发 singing 话题。路由使用纯用户话语，并接收与本轮音频 revision 绑定、只消费一次的结构化歌唱观测。实际唱过但歌词不含“唱歌”等关键词时，仍能加载相关技能；这不会建立角色回唱任务。完整时序、歌词和唱后请求仍进入正式模型消息。
2. **普通台词恢复增量发声。** 模型在正文前声明 `independent` 或 `after_action`。独立台词即使处在唱后追问窗口，也能在完整生成结束前进入 TTS 队列。依赖演唱或素材动作的台词仍等待校验；先选独立台词再追加此类动作会被拒绝，不能借即时发声绕过动作约束。保留旧输出格式的保守兼容路径。
3. **当前感知只送一份。** 用户消息保留完整听觉输入；程序感知放入本次临时上下文。用户轮、tick 和连续决策复用各自已经构造的当前帧，不再同时把整帧写入用户历史又追加一份。正式角色读取紧凑事项状态，独立审核器保留完整判定规则。快照按 epoch/generation 绑定；后来才返回的工具结果不会被较早的请求误确认。
4. **补齐延迟诊断。** `[LLM/Performance]` 区分原始输出首段、解析后正文首段、完整 prompt、服务端实际处理 token、缓存字段和 prefill；缺失字段记为 `null`。首个 TTS 文本块记录字符数。修正续接重置上一请求计时，以及用户事项在 tick 继续时丢失原首音统计的问题。

另修正两个状态一致性问题：同一用户输入不再重复重置事项；关闭再开启实时模式时，保留与既有聊天历史对应的最近对话、歌唱目标和播放证据，同时使旧工作回调失效。用户歌唱事项在 tick 中完成时按目标来源归属，不再仅按执行发生在哪种轮次分类。

## 同一公开样例的请求对比

测试通过真实最终 ASR 回调、技能路由和 ChatQW 请求组装，使用公开合成对话与固定公开角色说明。下表是完整消息的**字符数**，不是 token、缓存命中或延迟倍数。基线来自修改前已存在的隔离工程，保留源码哈希。

| 场景 | 修改前 | 修改后 | 减少 |
|---|---:|---:|---:|
| 启动后“早上好” | 49,492 | 34,726 | 29.84% |
| 连续闲聊第三轮 | 50,689 | 35,376 | 30.21% |
| 唱后第一句聊天气，仍在技能追问窗口 | 51,512 | 48,098 | 6.63% |
| 唱后第三条闲聊，追问窗口自然结束 | 52,557 | 37,021 | 29.56% |
| 实时模式停启后的闲聊 | 50,165 | 35,075 | 30.08% |

唱后头两轮保留技能追问窗口；普通台词已经可以流式入队，无需为了聊天立即卸载唱歌能力。真正有歌唱观测的轮次仍保留详细资料，缩减幅度相应较小。

依据：[完整对照数据](../../Logs/chat-latency-20260911/request-size-comparison.json)、[修改前公开请求](../../Logs/chat-latency-20260911/baseline-v2/chat-latency-public-requests.json)、[最终公开请求](../../Logs/chat-latency-20260911/fixed-v3/chat-latency-public-requests.json)。

## 隔离 Unity 验证

- 闲聊路径：63 项通过。覆盖启动问候、连续闲聊、没有话题关键词的实际歌唱观测、说话→歌词→唱后请求、唱后聊天、实时模式停启，以及未审核的演唱台词不能入队。
- 阶段解析：7,605 项通过。覆盖逐字符与不同分片、阶段/语言保留、非法阶段切换、独立台词后的依赖动作拒绝和执行投影不能复活动作。
- 传输与上下文：394 项通过。覆盖 SSE、性能字段语义、完整听觉输入、感知暂存失效、异步结果确认竞态、紧凑正式状态与独立审核规则。
- 生命周期：13 项通过。覆盖真实语音/文字输入只推进一次事项身份，模式停启保留最近回复与完成记录，旧回调失效，以及结构化声音观测不能被文字输入、下一次录音或重复消费错误继承。
- 既有技能路由通过；工作闭环、歌唱目标、审核传输/HTTP、自检及 Play Mode 六套共 524 项通过。

依据：[最终重点验证与哈希](../../Logs/chat-latency-20260911/fixed-v4/verification.json)、[完整闭环套件结果](../../Logs/chat-latency-20260911/fixed-v2/suite-results.json)。完整套件运行期间有一处提示词的合法元信息说明更新，因此其总哈希校验如实记录未通过；最终重点验证已经同步该说明、最终输出契约及忽略前置换行的计时修正，哈希一致。首次导入新增源文件曾出现临时编译错误；随后干净重跑全部通过。

这些隔离测试没有调用麦克风或 TTS 服务，也没有物理播放；“提前入队”不冒充“用户已听到首音”。

## 真实模型流式对照

使用上述两个版本实际导出的公开请求，各请求一次相同的六个样例；保持模型服务与槽配置不变，每次提交前确认服务空闲。测试顺序为修改后、修改前参考，各自首个请求均由服务端报告缓存为零，其余请求均报告复用 16,384 token。较早的 assistant 对话仍是固定测试历史，没有假称为完整真人会话。

| 场景 | 原始首段输出：前 → 后 | 实际重算 token：前 → 后 | prefill：前 → 后 |
|---|---:|---:|---:|
| 首次问候，无缓存 | 4.219 → 3.094 秒 | 25,335 → 18,501 | 4.069 → 2.961 秒 |
| 连续闲聊第三轮 | 1.750 → 0.578 秒 | 9,656 → 2,528 | 1.601 → 0.452 秒 |
| 唱后第一句聊天气 | 1.813 → 1.516 秒 | 9,836 → 8,316 | 1.659 → 1.399 秒 |
| 实时模式停启后的闲聊 | 1.718 → 0.562 秒 | 9,347 → 2,340 | 1.570 → 0.430 秒 |

数值来自实际 SSE 的 `usage` 和 `timings`，不由字符数推算。这是每例一次的功能/性能对照，不是统计基准；首段原始输出还包含内部格式标签，不等于正文首段或用户已经听见。

修改后的六例都输出了 `independent` 阶段，没有追加演唱动作。混合输入的实际回复为“青い空と、静かな夜ですね。とても穏やかな歌詞だわ。”，正确回答了歌词里的意象，并遵守唱后“不用回唱”的要求。另一段纯声音歌唱观测也回应了两句歌词。此结果证明公开样例的歌词进入了模型理解；没有据此声称模型已准确理解完整旋律或真实录音中的所有词句。

依据：[模型性能数值对照](../../Logs/chat-latency-20260911/model-performance-comparison.json)、[修改后原始网络采集](../../Logs/chat-latency-20260911/model-v1/model-stream-capture.json)、[修改前参考采集](../../Logs/chat-latency-20260911/model-reference-v1/model-stream-capture.json)。没有执行模型输出里的工具或调用 TTS。

随后把六例原始网络字节按实际分片交给 Unity 中的生产 `SSEDownloadHandler → RoleOutputChannels → ChatSample`，50 项通过。六例首块台词均在模型结束事件之前入队，且 singing 仍处于加载状态也不阻塞独立台词。按捕获时刻还原：连续闲聊的**有效正文首段/首块入队为 0.625 秒**；模式停启后的有效正文首段为 0.609 秒，首块入队为 0.641 秒。唱后第一句天气的有效正文首段为 1.594 秒，首块入队为 1.625 秒。尚未计入真实 TTS 合成和播放。

此次回放也核实了格式换行应保留而不算正文：修正相关埋点与测试断言后，全部非空白正文的语言和阶段正确，没有修改原文来使测试通过。依据：[生产回放结果](../../Logs/chat-latency-20260911/model-replay-v2/chat-latency-model-replay-regression.json)、[回放源码与证据哈希](../../Logs/chat-latency-20260911/model-replay-v2/verification.json)。

## 实际首音的验收范围

结构修复、请求缩减和真实模型生成阶段的改善已经验证。此前真实会话约 2.55–2.95 秒的停说至正式首音，仍需要在主场景用新的实际闲聊日志复测，不能由字符数、模型首段或脚本注入的流式片段推算已经恢复。冷启动及唱后技能追问窗口仍有较多输入计算，不能承诺每条闲聊都在半秒内开始回答。

下一次实际对话可以直接核对 `[Skill/Input]`、`[LLM/Performance]`、`首块切出 characters=` 和 `[Timing/Perceived] formal-first-audio`。服务端若没有返回缓存/处理时长字段，客户端会明确留空，不能把前缀匹配位置当成实际复用量。
