## 主要故障

### 意图编译与整段话的承诺不一致

| 对话实例 | 模型/运行时实际选择 | 问题所在 |
|---|---|---|
| c3 “走到我身边”；角色“了解。这就过去找你。” | `act/head.raise`，随后实际抬头 | 走近意图被编译成头部动作，LF160888 |
| c5 用户强调“没动，倒是抬头了” | 再次 `act/head.raise` | 重复错误，LF164243 |
| c29/c31 向左转身90度 | `head.left` | 身体与头部、转身幅度没有被保留，LF226154/230789 |
| c38 角色承诺重新点灯 | `head.raise`，随后实际抬头 | 开灯未进入设备执行器，LF250054 |
| c25 用户让靠近小灯 | `approach/current_user`，实际走向用户 | 目标消解错误，LF216036 |

这些错误标签是模型实际返回并通过解析的字段，不是本地 enum 默认值或字符串字段错位。`ActorIntentProtocol` 校验合法字段组合及 evidence 原文包含关系，不能保证引文表达的动作含义正确。`ChatSample.ActorIntent` 在一个头部动作被受理后，仍允许播放整个原草稿；这使“抬头受理”错误地授权了“走近/开灯”的整段承诺。

完整历史和空间执行反馈被带入分类上下文，可能影响分类，但没有同输入的提示词 A/B，不能断言某条旧提示是唯一原因。下一步应验证角色自己所选择的完整承诺与执行表示一致：动作域、目标、条件和剩余步骤必须得到覆盖；无法表达的部分交回完整规划，不能靠任意一个合法局部动作放行全部承诺。仍应保留角色拒绝、改变想法和自主行动的空间。

### 多步骤目标没有被持久保存

用户提出“转身→找到灯→靠近→关闭”，本轮通常只执行当前一步：

- c23只 turn-in-place；c24只 inspect-object。
- c34草稿明确表达“靠近并关闭”，实际 approach-object 到达后只确认新视野，没有续接 off。用户再次单独要求关灯，c35才成功。
- c41只 head.lower；c43只 look-at，后续没有 on 提交。

Room协议目前只输出单步 decision；`ChatSample.RoomTask.cs:307` 的本步回执分支会 return；`ChatSample.SceneObjectApproach.cs:418` 后续完成观察，并不持有设备操作的剩余目标。原请求文本虽存在，未变成待执行计划。需要程序持有同一个目标及当前阶段，按到达、图像和设备事实推进；每步完成不等于整个任务结束。这也能减少用户反复说同一件事。

### 两种停止回执错误

1. c9停止已发生，`poseReturning=true` 表示平滑回待机；`FastTaskControl.cs:128` 先允许自有姿势回落，最后又要求 `!Controller.IsMoving`，而 `IsMoving` 包括回待机动画。因此日志出现 `accepted=true, stopped=false`，用户却已看到停止。发布与播放前校验都要使用一致的“移动/跟随已停”的事实定义。
2. c7用户要求继续跟随，FastLoop错误提出 stop_follow，目标所有权检查正确拒绝；但 `FastLoop.cs:107` 仍直接发布停止失败模板并 return，吞掉原跟随请求。无效控制被拒绝后应回到完整当轮目标的普通判断/重规划。

独立停止语义复核在c9真实运行约0.380秒；c7因任务快照已过期，在调用复核前即被拒绝。不能把此次误跟随回执当成独立复核曾批准错误停止。

### 歌唱残余故障是来源、证据和上下文问题

- **c12未唱：** 编译器允许从历史 RequestEvidenceTexts 引用旧句，但 repeat 的 goal 校验要求证据来自最新用户原话。LF184773–184789因该不一致拒绝，尚未到达审核、队列、转换；不能归因于 range=clean 或RVC。
- **c17成功：** 当前引用通过，真正回唱第一段，用户下一轮确认。
- **c19唱错：** 当前录音已包含第二段分轨，新 `version=2/create` 决定仍选 `clip:18d53f7f-10`，审核随后批准该旧第一段，最终准备PCM与第一次来源相同。这是新目标选错源，不是旧回调越代。两轮都说“你能把这一段回唱给我听吗”，仅验证短引文存在不能绑定“这一段”属于哪次录音。审查通过不代表选中了用户最新目标。
- **c21无输出：** 用户再次明确“第二段”，LF205203报 `recording-required-evidence-over-budget`，必需证据超过32,000字符而中止。日志未记录必需块精确长度；不能拿一般 ContextSharing 总长度当作超限量。

应统一编译器与执行校验的证据范围契约；明确表达最新来源、旧活动目标与被替代目标，结构化保存必要的素材/版本/范围证据，避免反复附带整段历史直至超限。具体素材选择仍需模型判断，不能无条件用“最后录音”覆盖所有复唱请求。

### 感知/事实声明仍会漏过只读核验

c42模型编造 `wait/user_count_three`，程序正确拒绝无来源条件并转只读核验。该核验没有发送图像（LF259252），却公开说“看到了哦，那盏灯正亮着呢”（LF259440）。此后同一实体真实读回仍是 off（LF262274），没有任何 on 提交。

无工具权限、无标签并不保证自由文字中的状态断言正确。应限制核验能够公开的事实，绑定实际设备读回与图像来源；单纯合法 reply 不能替代事实一致性检查。本轮并非整体视觉失效：此前多次已收到当前图并识别到同一小灯。

### ASR异常丢掉了用户关于复杂指令的反馈

c37成功预览包含用户“为什么稍微复杂一点指令就无法同时执行”的完整反馈（LF245560），最终约49.35秒合并录音请求却返回500（LF246749），系统把它当无有效文本并恢复上一句“对对，成功了”（LF246841）。

只读读取 Spark `.163` 服务器堆栈，定位到 `identify_speaker → CAM++ → Conv2d` 的 `illegal immediate parameter (range error)`。声纹子模型异常未局部隔离，发生在正式转写之前而中止整个接口。读取时健康状态显示 ASR=cuda:0、speaker=cpu；无证据表明是本机算力不足。保存于 `asr-speaker-error.txt` 与 `asr-health.json`。

需要将声纹失败和ASR失败分开，并避免把服务异常记录为“未检测到人声”；来源未知仍需保留回声/打断约束。失败时不能把不完整预览冒充最终完整原话，也不能悄悄用旧问题替代新的反馈。

另有c11“我.”与c15“.”等弱输入，在原始VAD为0ms时仍被调性/演唱路径接纳，且已提前撤销正在准备的回复。用户也明确反馈杂音打断。未听原音，不能确定具体声源；应区分“保存可疑音频证据”与“确认新话轮”，保护合法哼唱和短应答。

## 建议下一轮实施顺序

1. **先处理确定的程序缺陷：** 声纹异常隔离与失败输入恢复，停止状态的假阴性，无效停止提案吞掉原目标，歌唱证据契约和必需上下文预算。
2. **补齐角色意图到执行计划的核心契约：** 完整承诺覆盖、正确身体域/对象、待执行步骤、阶段完成和取消条件。以本轮原样中文/日文对话验收，重点验证整项最终结果，不只检查JSON合法与单个动作受理。
3. **在同一任务身份上推进异步优化：** 让合法的空间预准备能够复用，尽早准备视觉/目标信息；独立的TTS、视觉和工具准备可重叠，实际动作按前置条件推进。压缩重复模型路由与审核，保留结果变化后的撤销机制。无需先迁移更多服务或更换主模型来解释这些失败。
