## 歌唱：生成和校验之间的确定性冲突

| 本轮输入 | 实际路由和选择 | 关闭录音到第二次拒绝 | 结果 |
|---|---|---:|---|

| c16：再试一次，回唱刚才那段 | recording_singing；两次 perform | 17.300 s | 同上 |
| c17：最后再试一次 | recording_singing；两次 perform | 17.944 s | 同上 |

六次拒绝的原始 LF 为87701、88271、90956、91526、93923、94493。六次 `recording_decision.context_bound` 均是新快照，包含当前用户、输入录音和素材清单；没有证据表明本次未绑定用户或未携带素材。

六份原始 JSON 都有非空 `speech.text`，如“了解。我会为你唱出刚才你录下的那一段歌声哦。”；但这个阶段的 perform 必须静默提交演唱提案。这些原始台词被拒绝，未实际播报，不能算角色已经公开承诺。另有五份 `source_evidence` 加了解释、额外引号、跨轮拼接，或只留下“用户当前连续原文：”前缀，未提供当前用户原话中的精确连续引用。

`RecordingSingingDecision.cs:64` 的 SourceContract 已要求当前连续原文、perform 空台词。`ResponseFormat` 的 source-aware 分支（约:94）却直接返回平坦 schema，`speech.text` 仍允许最多400字符，没有表达 perform 与空台词的关联。严格 JSON 生成只保证该 schema 接受的形式，不能保证未写入 schema 的客户端跨字段规则。

编译器约:280 在 source-aware repeat 时用 `source_evidence` 作为执行引用；随后把素材为空、台词非空、expected为空、引用为空或不在当前原文中等错误全部压成 `unbound-user-request`。因此这个错误名不等于“用户未授权”或“歌唱被禁止”。尤其 c16 第二份输出 LF91514 的 source 引用本来正确，单是台词非空就足以拒绝。

`ChatQW.cs:2812` 收到编译失败，只给出通用“结构化决策无效/请修正”并结束为 `<silent/>`。每次一次自动纠错仍生成相同类别的错误，随后到达重试上限。并不是用户输入没有到达模型，也不是模型六次拒绝演唱。

生产日志记录 `recording-singing-ir-v1`，说明新的专用录唱路径已加载。通用人格/口语规则仍可能诱导模型填写台词，但这是待做提示词对照实验的推断，不能把它当成已证明的唯一原因，也不能据此认定旧 XML 提示词接管了本轮。

## 非歌唱体验：物理执行有进步，结果反馈仍有明确缺陷

1. **走到用户身边成功，却播报未完成。** c9 LF62759 控制器 `arrived`，LF62781 `actor_plan.step_result.success=true`，随后LF62882却使用未确认完成的固定句。`ChatSample.ActorPlan.cs:221` 仅 follow 选择 CurrentActorTaskReceipt，其余走 CurrentRoomActionReceipt；后者支持 approach 受理/行进状态，但没有完成到达回执，返回null。:222把null直接变成失败台词。这是程序结果映射缺失，与用户观察一致。
2. **关灯已经成功，后续空步骤出错覆盖了成功事实。** c5 LF51403 是设备真实状态与新画面共同确认的 performed；后续规划返回 none 时仍带 actor_draft，被 RoomTaskProtocol 的作用域规则拒绝；修复返回 none 又缺失 planId/revision，再次拒绝。ActorPlan 的 invalid-room-plan-step 路径统一输出更正，错误否定前面已完成的行为。首音19.322秒并不代表全链完成；无效末次规划到关闭后72.517秒才返回。
3. **跟随已经运行，仍被重复规划和图像过期拖入失败反馈。** c10 LF66409 为 follow-waiting、success=true；remainingGoal却仍保留整段原话，继续规划同一follow。RoomTask在检查/复用已运行任务之前先要求旧图仍有效，约10秒模型请求返回时图像被判失效，重看一次仍失效，最终报无效步骤。该检查未记录失效时具体位移/角度，不能精确归因于画面年龄、平移或转角。复用同任务的逻辑存在于ActorPlan，却因检查顺序未能到达。
4. **“你一直在跟着我”触发了错误停止提案，但独立审核成功阻止误停。** c12 stop gate约0.290秒返回none，没有停止角色；随后FastTaskControl把整段话重新交Room，重复两次约10秒规划，最终27.098秒才以更正语出声。保住正确运行状态是进步，拒绝错误停止后的回退路径仍需缩短。
5. **语言继承有遗漏。** c10中文请求跟随，程序受理语却使用日文。ActorPlanReceipt的语言generation不匹配时直接fallback到ja，current-user-goal路径没有经过同样的语言绑定。需要沿用本轮实际语言事实。

c13明确要求停止跟随时，独立门控约0.355秒正确确认并停止。此前Fast判定接近6秒，才是这轮主要等待。已有的取消保护不应为了省这0.3秒而移除。

## 修复优先级和验收建议

1. **优先闭合录唱生成契约。** perform/handoff的公开台词由结构保证为空；按decision约束，避免重新引入旧的按range分支导致偏选ready旧素材的问题。精确引用可改为程序提供有身份的原话片段引用，由模型选择、程序回填原文，仍需验证当前指代与最新否定。不要用模糊匹配、删引号或跨轮猜测替代来源校验。
2. **细分错误与有界修复。** 区分非空演唱台词、来源引文不匹配、无素材、缺expected等错误；纠错准确指向字段。失败后按真实结果收尾，避免两次相同拒绝后只有静默。增加重试次数不能解决本次契约冲突。
3. **补齐动作终态与计划结束协议。** approach到达必须生成到达结果；后续步骤失败保留前面成功事实；none/计划完成有明确合法表达。对已经运行的同身份follow先核对和保留任务，避免因重复规划图像过期否定已运行动作。
4. **最后压缩关键路径。** 减少普通无动作对话的结构不一致复审、拒绝错误停止后的无必要Room回退，以及整段原话作为remainingGoal的循环。再针对单次约10秒Room请求核查上下文和输出预算。TTS预合成/语音与动作重叠已经生效，继续扩展并发应以任务身份和取消传播正确为前提。

歌唱验收必须分阶段：表格可编译 → 独立审核选择正确录音与边界 → 真实转换成功 → 实际播放且唱的是用户指定片段。至少重放“唱后直接回唱”“上一段重试”“讲话+歌声混合”“取消/否定”和本次c16错误开场白选材反例；不能以HTTP200或本地编译成功代替整条链路完成。
