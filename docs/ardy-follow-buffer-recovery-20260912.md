# 连续跟随缓冲、恢复与原房间诊断（2026-09-12）

用户已确认成功跟随的表现，并决定不增加手动测试场。本轮在现有跟随链路与房间窗口内修复断流恢复和诊断；没有修改房间、相机或新增手动场景。此前 `ardy-follow-room-review-20260912.md` 中独立手动场的建议已取消。

## 执行行为

- 起步和停稳后的重新起步先准备 0.8–1.2 秒已审核动作，再交给播放器。原生每次仍只采用 8 帧（0.4 秒）；不会播放 ARDY 回复中未经后续确认的预测尾部。
- 根据实际请求、规划、解析、审核耗时与近期帧间隔调整请求提前量，范围为 0.65–0.9 秒。一次性文本特征耗时不算作持续每段的生成成本，完整耗时仍保留在诊断里。尚未完成的请求不会借用上一请求的后端耗时。
- 临时缓冲耗尽时停止位移并平滑交回动画，保留上层跟随任务。在当前位置的实际姿态历史上开启新的原生动作会话，重新缓冲后继续。允许连续自动恢复 3 次；第 4 次断流明确结束，避免无限重试。连续正常播放 10 秒后恢复预算重置。
- 明确“停止”、断开或身体控制被接管仍优先取消；迟到的回复不能让旧任务重新起步。地形、用户身体净距及关节/位移质量检查继续生效，不能靠恢复越过检查。
- 消费已终止的控制器结果时，不再第二次取消而覆盖原故障原因。恢复中的跟随继续保留身体预约，等待期间的正常动作交接仍按既有生命周期处理。

预缓冲提高了对供给抖动的容忍度，也会增加部分起步和方向更新的等待；它不保证零延迟，不能弥补持续低于播放速度的生成供给。

## 在原房间查看

打开 **Tools → NeEEvA → ARDY Room Dialogue**，使用现有场景配置进入 Play。窗口的“当前运行观测”显示当前缓冲、恢复、跟随暂停、用户支撑面和视点高度；“动作请求耗时详情”显示请求往返、后端/排队、文本特征、Unity 规划/解析/审核、帧间隔及控制到实际播放的延迟。

Scene 的“空间诊断”使用运行中的同一导航与检查记录：绿色为验证通过的用户地面，青色为当前导航路径与目标，黄色为用户净距范围，红叉为实际保存的上次检查拒绝点。没有具体检查点时不推测位置。旧目标的拒绝会标为历史；当前地面有效也不等于动作已经生成。

窗口约每 0.25 秒读取观测，不在重绘时规划或接管角色。“检查当前地面与路线”是显式检查，不移动角色。关闭窗口不终止场景里的跟随任务。

日志新增 `[ARDY room/stream]` 结构化事件，包含请求、原生会话、上层操作和控制版本，便于关联各阶段耗时。历史异常与当前阶段分别保存；已有 `RoomTrace` 也附带动作流快照。

## 自动验证

证据目录：`Server/ARDY/runtime/stream-reliability-20260912/`。测试只使用既有隔离 Unity 自动夹具和真实本地 ARDY 服务，不创建给用户使用的额外场景。

已完成：

- `pure-r1`：统一 Unity 编译与持续路径/速度纯逻辑回归通过。
- `delay-r1`：真实 ARDY 回复经过仅延迟传输的 Editor 代理，4 个场景全部通过，共 8,153 项逐帧及生命周期检查。第二段延迟 900 毫秒时，缓冲前 root 位移为 0；单次后续回复延迟 2 秒时，同一操作恢复一次并继续；持续延迟时 3 次恢复后第 4 次断流明确结束；恢复期间停止后迟到的回复没有再次启动角色。停止阶段 root 漂移为 0，平滑返回均有多帧记录。
- `delay-final`：最终生产参数下重新运行上述 4 个真实回复延迟场景，全部通过，共 8,158 项检查；恢复次数分别为 0、1、3、1，恢复上限与明确停止边界均维持。
- `soak-final`：完整连续变速跟随、动态障碍和断网场景全部通过，共 45,641 项检查。主区间 60.000 秒、153 个短段、零断流，实际累计移动约 36.48 米；明确停止后 root 漂移为 0，约 0.433 秒交回动画。断网阶段一次供给恢复后收到实际请求错误，明确终止，没有持续播放缓存尾部。
- `stop-r5`：364 项确定性平滑停止、地形守卫、所有权与迟到结果边界检查通过。最终生产源码与该轮相同，之后差异仅在测试文件。
- `lifecycle-verified`：331 项受控聊天生命周期检查通过，包括 42 项故障身份/诊断断言。真实 Chat 指令、真实点头、实际控制器等待会话中，移动唤醒在派发前准确取消点头一次；恢复标志下不接管手势；明确停止后用户继续移动也没有重新启动，root 漂移为 0。此用例专门验证交接及取消，不替代完整原生行走到等待再出发的全链路验证。

保留的失败与修正记录：

- `soak-r2` 在主区间约 52 秒后遇到真实供给延迟；第 131 个请求发出时缓冲约 0.447 秒，等待约 0.366 秒仍未完成，剩余约 0.064 秒时进入平滑恢复。此前单次请求往返约 0.132–0.149 秒，末尾帧间隔正常。失败请求已取消，没有它的后端耗时，不能断言具体是重采样还是网络/后端原因。旧提前量下限 0.45 秒的实际交付预算只有约 0.38 秒，因此提高到 0.65 秒，给已允许的多候选生成留出余量。
- `soak-r4` 主区间完整运行 60.017 秒、153 个短段，零断流，动态障碍用例也通过。后续断网用例暴露测试夹具计算问题：关闭会话后，零缓冲被误解为已确认尾回退 0.05 秒。实际播放为 1.54999 秒，已确认尾为 1.55 秒。夹具现按同一个 clip 保留确认边界，并增加返回期 root 固定检查；未放宽未确认尾或主区间零断流要求。
- `chat-r3` 的真实点头后恢复发现 Bridge 唤醒条件落后于控制器：用户已经移动、请求速度仍为零时会先开始预缓冲，错过显式结束点头的窗口。两者现使用相同的唤醒条件；仍只在身体已释放的正常等待状态结束自身手势，不扩大到恢复中接管其他所有者。
- `chat-r5` 的 42 项身份/分类回归通过，但真实跟随第 5 个请求返回 `stream_quality_rejected`，中止了后续点头/停止验证。新分类已正确记录为 `motion-quality`，没有自动恢复、降低门限或采用坏动作。该次生成质量失败是仍存在的模型限制，不能因后续回归通过而忽略。
- `chat-final` 的身份检查仍通过，但初段跟随后发生用户净距保护：实际用户距离约 1.185 米；生成的未来检查点距当时用户约 0.644 米，低于 0.65 米要求，因此在播放前暂停。已承诺缓冲增加了近身减速的滞后，当时控制到播放延迟约 0.684 秒，不能把这一结果完全归因于随机生成。没有放宽净距保护；完整聊天走近、等待、点头、再跟随的严格用例本轮仍未全通过。
- `lifecycle-final` 首次受控检查在主动停止后复用了要求跟随仍活动的通用等待函数，导致夹具误报；点头取消一次和明确停止当时已通过。修正为逐帧验证任务保持停止及点头平滑返回后，`lifecycle-verified` 通过，生产代码未变。

最终生产源码由 `source-manifest-final.json` 记录；最后测试入口调整后的完整源清单为 `source-manifest-verified.json`。主项目仅需等待 Unity 编译完成后重新进入原房间 Play；本轮没有重启或更换 ARDY/Qwen 服务。
