## 具体故障和证据

### 1. 普通交谈被升级为物理任务

- capture 1 用户只问“喂喂喂，能听到吗？”（LF3770）。私有草稿“听到了哦，涅瓦在这里呢。”（LF4524）没有公开。Actor 以 `actor_goal_required` 拒绝（LF4732），实际播放“我更正一下：这个动作还没有确认完成。”（LF4899、5284）。日志未保存失败判定原始 JSON，不能断言是哪个字段组合导致这一错误。
- capture 2 用户明确说自己只是在打招呼（LF6080），下一份道歉解释草稿仍被归一成动作重规划（LF6971），goal 本身就是“通过言语道歉并解释……”。随后再次播放泛化更正（LF8310、8704、8904）。
- capture 4 的草稿是在说“别担心，只是机械性误会，我听得见”（LF10466），却因 `actor_domain_kind_mismatch` 被归一成 `other_action/replan`，Room 提交 approach（LF10921），实际 arrived（LF11074）。capture 5 用户随后追问为何突然走近（LF12305）。

源码：`ActorIntentProtocol.cs:158–181` 将多种跨字段失败统一转为 replan 或 claim；`ChatSample.FastLoopHandoff.cs:80` 再为 replan 设置 `purpose=plan`，随后登记 ActorPlan 并进入真实规划。`classificationUncertain` 目前只是提供给模型的描述，并不在程序控制流上形成独立、无物理执行权的复审阶段。`ChatSample.ActorIntent.cs:122–126` 的校验失败也直接通向动作更正，未区分普通对话。

这不是要禁止角色自主行动；真正需要保持的是“角色当前草稿采纳的物理意图”与“执行器提交的物理行动”一致。言语安抚本身不能被当作走近的决定。

### 2. 未来决定被误当作已完成声明

capture 9 的草稿“この小さなランプね。消すね。”是在说会关闭那盏小灯。Actor 却给出 claim（LF22345），代码走 verify-only 并给出通用“尚未核实全部动作结果”话术（LF22477、22881），没有执行关灯。

未来决定、动作进行中和动作已完成必须区分。不能通过把所有不确定项都拦成更正来获得表面上的事实一致；也不能为证实过去完成声明而补做动作。

### 3. 多步计划只有部分路径真正续接

capture 8 的完整目标是左转、找灯、关灯（LF18776）。Fast 选择 legacy，Room 完成 `turn-in-place/view-change-completed`（LF19772），随后只说“我已经看向那里确认了一下”（LF20496）。本轮没有注册 ActorPlan 保存和继续后续关灯步骤。

capture 11 则确实出现 inspect 成功后提交同实体 set-object-state（LF27508、27719），说明上一轮的计划续接并非完全没有工作。但一个入口能续步不代表 legacy、恢复和普通回复出口全部接通。

### 4. 关灯目标被偷换，且视觉验证失效原因不是简单超时

capture 11 的第一次目标匹配将用户说的灯解释为发光屏幕，并判 matched（LF27402、27412）。被绑定实体记录的能力只有 `inspect-object` 和 `look-at`，没有设备状态写入能力（LF27437）。这不能证明真正的装饰灯不存在或不能关闭，只证明这次绑定的对象不满足目标。

下一步 Room 推理结束后，旧图约 9.75 秒，程序已经刷新图像（LF27647）。最终失败时新图仅约 **2.97 秒**，`bindingCurrent=true`，但 **`viewCompatible=false`**（LF27669）；最终输出的 `object-target-expired` 是综合失效名称（LF27705）。源码兼容检查包含相机位移和朝向阈值，日志未记录具体差值，因此无法确定是位移还是转角超限。

不能仅增加过期时间或关掉当前视图校验。需要保留原物体语义、绑定设备能力，并协调目标验证期间的视角变化；视图变化后应以新图重新绑定同一目标。

最后 capture 15 的候选是屏幕、电视框、墙、窗、电视柜和地板，没有匹配目标灯具，`different-target` 拒绝（LF36422）是合理的。错误在更早的目标寻找/计划与能力连接，不在这一次拒绝本身。

### 5. 无效输入恢复绕开动作链，出现已播出的空承诺

capture 13 用户完整要求左转九十度、靠近灯并关闭（LF30614、30716）。capture 14 开始时取消了原 ActorPlan（LF31556）；之后该候选被 ASR 判为无有效人声（LF32191），并没有形成新文字问题。

`InputRecovery` 恢复旧问题（LF32264），但新 generation 没有新图绑定（LF32293），走 `General/work-feedback`（LF32514）。最终公开并播出“我现在向左转九十度……靠近”“找到后我会直接将它关掉”（LF33359、33460、33730），只输出旧的 look/motion/next 标签，没有对应 Room 转身、靠近、关灯受理。

源码：`ChatSample.cs:7487` 的 `ResumePendingReplyAfterEmptyInput` 使用 `continueExistingUserTurn:true`，经 `4838` 分支进入 `DispatchFormalContinuation`（`4984–5030`），直接调用 `PostSpeechFeedbackStream` 和普通语音 delta 出口，未重走 FastLoop/Actor/Room 编译。应保留旧请求的所有权、已执行事实和未完成目标，通过与正常输入一致的动作入口恢复，而不是只恢复文字生成。

### 6. 并行工作存在，但当前没有转化成体验收益

本轮 7 次 Actor 并行私有 TTS 都在判定结束前备好了音频，但 6 次因 planner handoff、1 次因改口被丢弃，直接复用为 0。进一步加速 TTS 对主要等待帮助很小；先让普通回复走对分支、保留可发布草稿，才会获得并行收益。

结合原始文本和 trace，Room 预准备共 6 次提交，5 次约 2 秒后客户端超时，1 次取消，未采用。最早一次提交没有绑定 trace，只数结构化事件会漏掉它。根因已定位到 `ChatQW.RoomTask.cs:39` 的独立传输槽仍硬编码 `request.timeout = 2`；失败对应 Curl error 28、2000 ms、0 bytes received。上层后台准备预算变长没有改变这一实际 HTTP 超时。后续部分话轮仍另发正式 Room 请求，形成无收益的额外请求；日志未测量额外请求造成的实际 GPU 排队，不能给争用成本编造数字。其余阶段仍存在 Fast → Actor → skill route → Room → 目标匹配 → 下一 Room 的串行等待。

ASR 在本轮未复现上一轮的 HTTP 500/声纹异常中断。最终文本基本保留了用户连续纠正和多步关灯要求，但转写里仍有“他/它”、重复字、断句和末尾 Yes 等现象；没有对应原音听辨基准，不能计算识别准确率，也不能断言末尾英文由模型凭空添加。

## 建议的修复顺序和验收

1. **先消除普通对话升级成动作的回归。** 语义复审与物理规划分离，字段校验失败不能默认赋予执行目标；普通听见/看见/道歉不得生成动作未确认回执。用这轮真实问候和纠正做闭环验收，不能只检查 JSON 可解析。
2. **统一任务入口与恢复。** 正常、legacy、空输入恢复、动作后反馈均保留同一原始目标、已执行结果和剩余步骤；恢复输出的行动承诺也必须对应受理的动作。先修恢复绕过，避免继续扩展两套出口。
3. **修正目标与视角生命周期。** 保留“装饰灯”而非宽泛“发光东西”的目标；确认实际设备实体与可用能力；记录导致 viewCompatible=false 的位移/转角数值，并在视角变化时重新验证同一实体，不能靠放宽失效门通过。
4. **在正确路径上减少等待。** 将不依赖动作完成的普通解释与执行并行；任务受理后可发布与当前计划一致的将来行动语句，完成声明仍等待执行结果。复用并行 TTS，修复预准备有效超时、避免重复 Room 请求，并修正按话轮归属的首音计时。
5. **使用本轮真实序列做端到端回归。** “能听见→用户纠正”“纯安抚无身体决定”“我这就关灯”“左转→找目标→靠近→关闭”“中途无效录音→恢复同一计划”“目标验证期间相机变化”“明确拒绝/选择其他行动”都应检查实际公开文本、动作受理、执行结果与下一步，不能把全部测试简化成服从用户指令。

歌唱需要另做有意的实测；本轮不据此更换或重新部署模型、ASR、TTS 或 SVC。
