## 实际修复

### 录唱素材与独立审核

1. 专用录唱上下文不再因为声学分类为 speech、歌唱分段文本为空，而隐藏旧录音的完整转写并剔除其候选 key。最新会话 c15 中真正唱过的录音因此仍可被 c16/c17 的回唱请求选择，后续催促录音不会天然获得优先权。
2. 保留真实录音身份、版本、完整转写和候选边界；普通 Fast 上下文仍是最多六条索引，专用材料表有 32,000 个 UTF-16 字符硬上限。需要时无损提取重复字段名，超限明确失败，不静默截断证据。
3. WorkReview 的发送 schema 和接收解析使用同一份定义。`singing_goal_expected` 的七字段（包括 `source_relation`）一致，修复原先发送七字段却只接收六字段的程序矛盾。
4. 审核不可用首次显示系统错误并只重试一次；再次失败停止后台自动重试、保留目标和素材、明确尚未提交转换/播放。重复回调、旧目标版本和旧轮次不能消耗新任务预算或改变新任务。
5. 后续 Fast 上下文保留历史审核故障事实，标明是否仍属于当前目标，不将其误投影为缺少用户许可或转换服务失败。

这仍是录音转角色声线的 SVC 路径，没有启用 SVS。材料可见、提案通过、独立审核通过、实际转换和播放是不同阶段。

### 动作执行与等待时间

1. Spark 的 OpenAICompatible Room 请求真正发送 `json_schema`；解码约束与接收器同步，走近不再能填写跟随专属 `planContinuation`。
2. 当前用户的原子走近/跟随任务使用请求前捕获的程序绑定，重新核对用户、角色、控制器、导航、任务 ID 和代际；不再依赖从未由程序赋值的 `TargetIsProgramBound` 标记。
3. 经现有 Actor 裁判接受的原子走近/跟随可直接进入真实控制器，省去额外 Room 模型请求。原子走近由程序建立有限单步计划，实际结果 watcher 确认完成后终结；不让模型把同一句原稿重新填成未完成目标。
4. 泛化物体任务和复合目标保留完整规划路径。已停止的自主移动不能靠晚回调重启；另一个人的原子目标不能改指当前用户。
5. 动作已经完成时不再补播迟到的“开始尝试”。失败/未提交/到达/持续跟随仍分别依据真实结果反馈。

这些改动减少串行模型调用和无效排队；本轮没有测量主场景新的端到端首音，所以不据此承诺具体首音秒数。

### Fast 控制与重复回复

1. 每次 Fast 请求只开放当前实际存在的停止类型及准确任务 ID；任务已完成时，schema 根本没有旧任务的停止分支。接收器也验证快照，防止兼容后端忽略 schema。
2. 停止提案被拒后，恢复请求保留完整输入和实际执行事实，但不再开放另一次身体停止提案，避免重复失败循环。
3. 长文本重复只触发一次恢复。恢复先引用当前关注点，再区别当前回应与用户明确要求逐字重复。若仍无依据地重复已说过的长句，停止发布该草稿，用有界的真实失败说明收尾，不再让用户“换个说法”。
4. 正常对话没有增加额外必经模型审核，现有 TTS 准备并行路径继续保留。
