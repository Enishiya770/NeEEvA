# 从交流意图到掌向与动作

用户期望的是“打个招呼”能够自动变成合适的身体动作。上一阶段的 `compose` 解决了指定姿态与局部动作的执行，但默认掌向沿用旧手腕基准，缺少面向交流对象的手掌目标。这一阶段同时补充可执行的掌向与规划时的意图补全。

## 规划与泛化范围

规划合同要求 Qwen 根据交流目的选择可观察的动作形式，并保留用户明确指定的约束。对于带姿态要求的问候、告别或示掌，可以选择掌面朝向交流对象、合适的肘弯曲与局部摆动；用户指定掌心朝下时，这一明确要求优先。没有姿态约束的基础手势继续使用已验收资源，开放式身体运动继续走 ARDY。合同表达的是目标行为，实际规划仍会有遗漏和误选，不能假定每次都遵守。

新接口让同一套控制器组合多种掌向和臂姿态。这属于意图规划与可组合执行能力，不等于 ARDY 学会了所有新动作，也不能用少量规划样例代表开放场景的动作自然度。

明确掌向但未指定肘角时，肘角作为可求解的自由度：执行器在 0–110° 内搜索满足掌向与局部动作限位的准备姿态，优先保留腕部余量，然后固定这个解执行。无掌向的旧计划仍默认 8°；`current` 和明确填写的肘角保持固定。Qwen 不必猜出一个精确角度，但必须正确区分用户的明确约束与可自行选择的细节。

## 掌向与身体配合

`leftPalm` / `rightPalm` 支持 `keep`、`partner`、`up`、`down`、`inward`、`outward`。掌向表示掌面法线，区别于手指指向；`keep` 不增加掌向约束，保留已有动作行为。手掌基准由实际 Humanoid 手腕与手指根部骨骼推导，不假定模型手骨的某个局部欧拉轴就是掌面。

显式掌向同时调整前臂的轴向转动与手腕方向，保持指定的手臂方向、肘角和手腕位置。项目限制腕部 swing 为 80°、前臂轴向 roll 为 180°；这些是执行器的工程限位，不是对人体活动范围的医学判断或完整关节力学模型。超过限位会报告失败，不通过暗改用户的明确约束强行完成。

双臂几乎完全向前伸直时，再要求掌面正对前方，可能需要很大的腕部弯折。自主选择问候姿态时可适当屈肘或改变抬臂方向；若用户坚持明确的伸直角度，就必须保留并如实反馈可达性冲突。

`axis="palm-normal"` 在掌面内摆动手掌，保持掌面朝向；只适用于已经指定掌向的活动手腕。其他旋转轴仍保留，用于不同的动作目的。

## 交流对象与反馈

对话连接面板和姿态面板均可指定交流对象的位置。留空时使用主相机；如果没有主相机，执行器以角色正前方作为降级方向，并在观测记录中标明。对象位置在动作开始时采样，持姿不会自动持续追随移动中的头显。

对话中的目标以 ARDY Dialogue Motion 面板的 Bridge 配置为准，会在每次动作请求时同步到 Controller。独立姿态预览面板的目标不自动同步到对话连接。

控制器保存 `lastControlPlan`、`lastControlObservation`、`lastControlError`，使下一次已有的聊天或自主决策能看到未达标原因。历史观测不代表当前仍保持姿态，拒绝也不能解释成已执行。规划只能调整用户没有明确限定的自由度；这一机制不添加无限自动重试。

入口格式错误由 Chat 独立记录为 `lastMotionProtocolRejection`，带原回复轮次与序号，不冒充 Controller 的执行失败。普通无动作交流会保留这一历史记录；后续合法指令、能力切换、断开重绑或禁用清除。JSON 中没有的计划和观测保留真实 `null`，避免 Unity 序列化凭空产生默认对象。

XML 不允许同侧 `current` 与显式 `Bend` 同时出现：前者要求保持实测姿态，后者要求新肘角，不能静默覆盖其中一项。直接 C# 调用的 `current` 始终采用实测值，默认数值字段仅是占位。

## 验证

首轮公共输入“双臂向前平伸，用双手跟我打个招呼。”的真实 Qwen 输出自行选择了双臂 `forward`、两掌 `partner` 与双腕 `palm-normal`，没有填写肘角。原始标签未经手工修改，经生产解析器产生自动肘角自由度，实际 ChatSample 事件、Bridge 与 Controller 驱动两个真实 VRM 的 Humanoid / ControlRig，共四组角色朝向与缩放组合。

主例四组均完成两次摆动并回到待机，自动解算肘角为 40°；独立实际掌面量测最大朝向误差低于 0.25°，最大手腕 swing 约 68.1°。输出是本地约束控制器执行的真实 Unity 帧，不是新的 ARDY 样本，也不包含姿态修图或帧间插值。记录见 [主例预览清单](../Tools/MotionAdapter/reports/palm-execution-v1/primary/preview-manifest.json)，[实际角色回放](../Tools/MotionAdapter/reports/palm-execution-v1/primary/fixture-0-public-qwen-zh-forward-greeting.gif)。

最终完整掌向回归通过 42 组实际实例测试，覆盖两套 VRM、不同朝向与缩放、侧方/高位目标、相机降级、当前持姿、掌向变换、固定角度边界、缺失手指映射及失败反馈。独立实际掌向误差最大 0.2495°，正例腕部 swing 最大 79.739°；进入准备阶段也记录实际腕角。固定 8° 在测试目标下属于余量很小但可达的正例，固定 0° 属于明确不可达负例，不将所有直臂姿态一概判为失败。完整结论见 [验收摘要](../Tools/MotionAdapter/reports/palm-execution-v1/acceptance.md)，[最终主例回放](../Tools/MotionAdapter/reports/palm-execution-v1/final-previews/fixture-0-public-qwen-zh-forward-greeting.gif)。

最终兼容性检查也已通过：骨骼锚定 15,794 项、流式协议 162,723 项、真实 ChatSample 1,303 项、实际 Animator/VRM 回放 756,965 项。真实 HTTP 联调收到 3 窗共 120 帧，首窗约 0.99 秒，取消与结束均回待机；这是通道与时序检查，不是该自由动作的语义/自然度评分。见 [聊天检查](../Tools/MotionAdapter/reports/palm-final-legacy-dialogue.json)、[旧动作回放检查](../Tools/MotionAdapter/reports/palm-final-legacy-playmode.json)、[在线生成检查](../Tools/MotionAdapter/reports/palm-final-live-http.json)。四个已验收动作资源及当前适配器、发布清单 SHA256 均未改变；最终源码、隔离工程及报告绑定于 [证据清单](../Tools/MotionAdapter/reports/palm-execution-v1/source-evidence.json)。

规划开发中保留了每版合同、原始请求和响应。紧凑单一规范候选恢复了自由动作路由及标签合法性，却让同一主例自行填写 `Bend=0`，反而锁死执行器自由度；另有漏摆腕、日文方向误解、收到不可达反馈仍重提旧姿态的问题。这些是尚未解决的规划错误，不能因为标签通过解析就记为动作成功。

因此当前采用首轮已实测的完整合同，逐字恢复并只注入一次，保留其正确主例和自由生成路线。它仍有单臂前伸约束丢失、旧掌向过度保留、日文侧向示掌误选等缺陷；未对恢复版重复运行那四条候选版本的留出表述，也不把它们计作恢复版的泛化证据。版本选择与未通过候选见 [合同选择记录](../Tools/MotionAdapter/reports/palm-purpose-protocol-release-selection.json)。

执行器只知道收到的结构化计划，无法可靠判断一个数值到底是用户坚持的要求还是模型自行补充。它保留明确写入计划的约束，不会为了做出动作而一律抹掉肘角。后续通用规划需要显式维护用户约束与自主选择的区别，并以执行可达性反馈校验；继续堆叠提示词不能代替这一机制。

`compose` 内的实际持姿接续已有验证。跨到 `generate` 时仍有一个独立限制：等待首个服务窗口期间会先淡出持姿，服务初始历史与接管时姿态可能不同；本阶段未更改这一流式交接流程。它不应被解释为任意自由动作都能从当前持姿无缝续接。

## 用户自然度反馈与阶段建议（2026-09-10）

用户对最终双手招呼回放的反馈是“手部摆动速度太慢，不像人”，期望更轻快的招呼。此例的状态是：几何与通道验收通过，问候节奏的用户验收未通过。原始测试报告和回放保留，不把几何通过升级成自然度通过。

直接原因可以定位：原始 Qwen 标签选择 `cycles=2`、`seconds=3.2`、`amplitude=10`，即每秒 0.625 个往返周期、每周期 1.6 秒；执行曲线前后各 15% 渐入渐出，分别约 0.48 秒。71 帧 GIF 总时长 4.62 秒，原生首末帧跨度约 4.586 秒，差异包含末帧停留与时间量化；文件没有被额外慢放。这是 `compose` 参数选择与通用曲线的表现，不能直接当作 ARDY 原生动作网络的速度评价。

建议进入意图规划与节奏控制阶段，暂不继续围绕这一条回放手工调参。本轮不更改模型、运行参数或已验收动作资源。该例保留为必回归的自然度失败用例：后续修复必须能从自然语言意图自主得到更合适的节奏，不能把手填参数后的改善当作泛化成功。

下一阶段应共同处理三个问题：

1. 区分用户明确约束与模型自主补充的细节，保留跨轮纠错后的方向、掌向和动作目的。
2. 将节奏作为独立规划维度，协调周期、总时长、幅度及起止过渡；按关节与动作目的选择节奏。用户之前对轻微点头、摇头的偏好不应成为所有手势的慢速默认，也不应通过全局加速破坏这些已接受的动作。
3. 用多种问候、告别、静态示掌、指示和头部交流动作及未调过的表述共同验收，分别记录意图遵循、实际可达性与用户感受。不同情境允许不同节奏，不预设“所有打招呼都必须一样快”。

若后续仅做节奏对照试验，可以在现有频率边界内改变时长，但它只用于验证速度对观感的影响。本阶段不为某一句话写专用分支，不再次训练 adapter；恢复训练应以新证据表明原生动作网络是相关瓶颈为前提。
