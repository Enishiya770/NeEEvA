# 对话中无语音、无动作的日志诊断

2026-09-10，依据最新主项目 Unity `Editor.log` 快照。原日志 SHA256 为 `252576b80d8905a6955387da3d76ca16ee38843a0193cc3953d9c07929494dcc`，保存在 `Logs/motion-silence-20260910/Editor.snapshot.log`。下面只引用公开执行通道和运行状态。

## 直接原因

本场有五次动作协议拒绝：四次 `compose` 使用了不支持的 `palm="partner"`，一次使用了不存在的 `name="bow"`。当前协议使用左右分开的 `leftPalm/rightPalm`；鞠躬需要通过生成或有效计划表达，不是一个已注册的基础动作名。

五次拒绝之后都实际发出了 `IssueMotionRepair` 请求，也都进入 `CompleteMotionRepair` 回调。因此不能归因于修订请求没有发出、模型连接中断或 ARDY 返回错误。失败动作在解析层已被拦住，未提交给 ARDY。

本次静默的完整链条是：

1. 模型输出了无效动作参数，动作被拒绝。
2. 新增的拒绝处理清掉该轮尚未播放的语音，避免继续播报动作已经完成。
3. 五次自动修订都没有返回公开台词或动作。输出分流器把没有公开内容的结果表示为 `<silent/>`。
4. 修订回调只检查原始字符串是否为空，`<silent/>` 绕过检查，后续去掉标签才变成空正文。空语音队列直接结束，没有明确失败结果。
5. 原流式回复又被通用收尾逻辑标为“异常路径（文本－空管线）／本轮已回应用户”，有些被抑制的文字还进入了已说历史。

日志中的 TTS“失败／跳过”和 `Curl error 42: Callback aborted` 在这些轮次里是清除、取消链路的后续现象，不能据此判定 TTS 服务故障。“异常路径（文本－空管线）”也是本地收尾标签，不是模型返回的异常。

这属于上一阶段新增动作反馈与语音流程衔接的缺陷。原指令本身确实无效，但不应该因此让用户只等到一整轮静默。

## 已修改的处理

- 动作修订只返回空内容、`<silent/>` 或其他无动作的控制标签时，明确记为修订未完成，不再进入空语音播放，也不再自动增加重试。合法纯动作回复和非空的限制说明仍允许；普通聊天中角色主动选择沉默不受影响。
- 被拒绝并抑制的正文不再被该轮收尾代码登记为已经说出。拒绝、修订失败和成功回复分开收尾。
- 没有自动修订的执行拒绝，以及修订最终没有结果时，通过独立系统提示显示失败。该提示使用默认 `ErrorsOnly` 模式可见的错误级别，不伪造角色台词；用户明确选择隐藏系统提示时仍尊重该设置。
- 错误信息指出未知字段并列出允许字段，让模型知道 `palm` 与左右掌向字段的区别。没有偷偷把不明确的指令转换成别的动作；例如只控制头部、两臂都是 `none` 时，给两侧补掌向仍是无效计划。
- 给动作修订单独增加反馈请求接口：常规角色规则、记忆和合同保持原有位置，短执行失败事实放在已完成的角色答复之后。原来这些新事实被放在最后一条用户消息之前，后面却保留了被拒绝的答复，时序不符合“执行后反馈”。普通对话与其他原有续接接口的位置不变，也不追加虚构的用户发言。

反馈顺序是促成空返回的原因候选，需要公开对照与实际使用验证，不能仅凭代码推断认定它独自解释全部模型行为。明确失败收尾则独立于模型是否配合：即使后续修订仍为空，也必须给出真实系统结果。
