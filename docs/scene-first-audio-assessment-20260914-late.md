# 最新 Play 评估与 1.5 秒首音方案

本次仅核查日志、代码并设计下一批，没有修改运行代码、场景或服务，没有新增模型请求。日志冻结于 2026-09-14 22:15，源文件最后更新 22:13:30 JST；评估最后一次约 21:59–22:13 的 Play 会话。原始 LF 行号 163725–197260；SHA-256 及复制时间见 [source.json](../Server/ARDY/runtime/scene-play-review-20260914-late/source.json)。

## 结论

房间的来身边、持续跟随、停止能执行，但这一轮不能评为“只有延迟问题”：正式语音有瞬间取消、内部执行文字误播，以及一次 TTS 超时；合并两段回唱也未进入执行。下一批优先级应是**可靠首句与首音链路重构**，暂不扩展新的场景交互能力。

1.5 秒保留为目标，口径为“实际停说→与问题有关且可听见的正式内容”。现有链路没有接近达标；不能靠调短一个等待参数实现。需要在用户说话期间准备，减少停说后串行模型请求，并保证候选不会在改口或事实变化后被误放行。

### 语音可靠性问题

1. **三次缓存开场之后，正式第一句 PCM 刚开始便失败。** 配对为 LF164511→164901、165929→166278、192104→193719；没有对应第一句自然播完。这些首音时间不证明用户听见了有效回复。
2. **开场交接存在与日志高度吻合的竞态。** `ChatSample.GetFormalPlaybackPermission`（当前源码 4979 行）仅用开场标记加共享 `AudioSource.isPlaying` 判断开场是否还在播。`GPTSoVITSFASTAPI.StreamVoice`（559–591 行）开始正式 clip 后立即再次检查播放门，而调用方尚未来得及在 `MarkRealFirstAudioStarted` 清掉旧开场标记；正式音频可能被误认成超时的旧开场而取消。三次一一对应是强证据，但本次未做可执行复现，仍须在修复前用确定性测试确认。
3. **内部执行文字进入公开语音。** LF180515/180527 中模型回显的内部事实被归为 1618 字 speech；第一段 32 字进入 TTS，并有自然完整播放 6.46 秒的程序记录（LF181045）。后续大段只有开始播放证据，最终 Request timeout（LF181383）；不能称整段都播完。
4. 本轮有 8 次发声阶段校验失败、4 次最终纠错兜底、2 次无进展停止，部分属于同一事项，不能相加为失败轮数。HTTP 200 后的流超时、主动取消、格式错误也必须分别统计。

末尾 122 条 Unity UIElements 文字顶点超限警告来自超长日志显示，不是 ARDY/Qwen 崩溃的证据。

17 次用户房间决策有 **14 次最终为 none**，普通问候、讨论回复速度也先花 2–3 秒判定房间任务。之后 General 请求携带约 2.95–4.31 万 token，实际缓存字段一直为 11483，仍有约 1.8–3.2 万 token 重新计算。歌唱失败还会接多轮纠错/审核，形成 20–39 秒长尾。

最后三条场景请求的估计停说至正式首音为 **11.27、12.99、12.34 秒**。例如“来身边”在程序 EOU 后依次经历决策 2.512 秒、首段动作准备 1.95 秒、正式模型请求 3.567 秒、TTS 0.61 秒，总体 9.03 秒。跟随回复另做两次约 1.6 秒审核，遇目标事实变化后回退。

上一批输入阶段裁减仍生效，但上一批固定文本测试不含麦克风、任务组成也不同，不能把两批中位数直接当作优化收益或回退幅度。

## 1.5 秒方案

### A. 先修可听性和台词边界

- 开场 clip 与正式 clip 分别绑定所有权；交接完成后不能再用共享播放器的播放状态推断旧开场仍在播放。取消仍能停止自己这一代音频，不能误停新一代。
- 公开台词采用明确、可增量解析的输出边界，内部事实/工具记录不允许作为默认正文落入 TTS。结构约束只解决格式，语义上是否符合事实仍按实际依赖核验。
- 首音埋点保留“请求播放”，增加实际 DSP/音频进度及录音回环验收；立即失败单列，不能算成功送达。记录首句内容，排除只有笑声、称呼、泛泛应声的情况。
- 将此次合并录音未提交、阶段冲突、内部记录回显做固定反例。至少保证快速回复能准确解释当前失败状态；不将完整歌唱系统扩展混入延迟小批次。

### B. 同一 Qwen 直接决定通道并生成首句

普通聊天不应固定经历“完整空间规划→none→第二次长模型请求”。建议由同一 Qwen 的一次正式请求输出短的结构化决策头和正文，明确本轮需要普通回答、现有事实回答还是工具执行。决策头验证后，独立正式台词即可走已有流式 TTS；动作仍按自身的几何、对象能力与执行检查提交。

这不是用中文关键词封死动作能力，也不是让程序代替角色决定说什么。Qwen 仍决定内容和意图；缩短的是一次次重复读取全套状态的流程。

首句保留人设、语言、完整当前原话、相关记忆、指代和未完成事项；完整世界与歌唱证据保存在状态层，按任务提供必要部分。不能为满足 token 预算丢弃尾句否定、刚新增的录音或失败原因。若本轮确实需要大量证据，走较慢路径并如实计入未达标。

稳定上下文应尽量复用，频繁变化的观察和本轮输入置于适当位置，并检查实际 `prompt_n/cache_n/prompt_ms`。所用 llama.cpp 固定版本支持前缀缓存与上下文检查点；这些机制不等于某次请求一定全量命中，参数与多模态场景仍需实测。[官方固定版本说明](https://github.com/ggml-org/llama.cpp/blob/dc80c5252a6d49301726e5987cc1fa006b69d93e/tools/server/README.md)

### C. 把准备工作移到倾听期间

复用已有流式 ASR、倾听草稿、完整预测 ASR 和精确文本音频缓存，让同一 Qwen 在稳定语音片段期间准备相关事实、候选首句与必要审核，必要时提前合成音频，全部保持私有。

真正收束时检查最终音频覆盖、转写版本、事实版本与候选依赖。输入完全一致且核验仍有效才提交；追加“不”、换物件、继续唱或用户再次开口时撤销。不能以已有的文本相似度门代替最终语义授权。只保留有界的最新准备任务，正式对话优先；多个槽仍共享同一张 GPU，盲目并发可能更慢。

收口必须与输入准备一起优化。当前约 1.96 秒本身已经超过目标，不能保留这个等待再要求后续链路达到 1.5 秒。目标是在明确说完的普通交流中更早确认；停顿、歌唱换气和不确定语音继续听，超时如实记，不通过截断用户来达标。

### D. 把结果报告和及时说话按真实依赖安排

已经有依据的回答可先说；需要走近才能看到的文字、尚未到达的位置、尚未播放的歌声不能预先宣布成功。例如“刚才两段各自能回放，但合并任务还没提交成功”可基于现有执行记录回答；“已经连起来唱好了”必须等实际结果。

对动作请求，可以很快表达具体意图并启动执行，但这种计划话语另记为“任务承接”，不能自动充当用户问题的实质答案，更不能当作动作完成。目标仍是缩短真实回答，不能靠一声“好的”达标。

依赖事实审核的精确首句可在审核期间私有合成，审核通过、语言/音色/事实/轮次都匹配才播放；拒绝就销毁。这样能隐藏部分 TTS 等待，但按本次约 0.61 秒 TTS 成本，它只是辅助优化。

## 预算与验收

以下是**热服务、普通交流、无需等新外部结果**的工程预算，尚未实现或测得，不是对所有请求的承诺：

| 停说后的关键链 | 目标 |
|---|---:|
| 确认轮次结束、最终输入就绪（主要工作提前完成） | 0.35 秒 |
| 本地版本/事实提交核对 | 0.05 秒 |
| 同一 Qwen 正式选句到首个实质块 | 0.55 秒 |
| 首句 PCM 就绪，或复用精确预合成 | 0.35 秒 |
| 实际播放与调度 | 0.10 秒 |
| 合计 | 1.40 秒，留 0.10 秒余量 |

任何仍需新增的视觉编码、语义审核、检索等待都必须纳入关键链，不能隐藏在预算之外。完整原话或必要证据很大、冷启动、改口使准备失效、第一次看到新对象时，不能承诺硬性每轮 ≤1.5 秒。

建议先做一批有界原型：修复上述音频交接与台词边界；建立同一 Qwen 的普通正式首句路径，验证缓存与增量播放；再接听中准备和较快收口。先证明一组真实普通问答在保留人设/记忆/能力的条件下能逼近目标，才扩展视觉、动作和歌唱的相关首句。

验收固定普通聊天、唱后转聊天、已知场景问答、新对象、动作命令、改口/打断、冷启动与 GPU 忙时样例；原录音、首句文本和真实音频起点关联。分别报告 P50/P95、≤1.5 秒占比、无声/误播、误抢话、候选撤销和任务提交情况。以热普通对话 **P95≤1.5 秒**作为第一项验证目标，其余类别不剔除，单列未达原因；同时保留首次任务承接、动作开始、动作完成和歌声开始各自的计时。

9 月 11 日曾有热普通对话有效正文约 0.625 秒的真实网络回放证据，说明同一模型值得继续验证；它不含真实收口和 TTS，不能当作已经达成过 1.5 秒。详见 [历史验证](reviews/2026-09-11-chat-latency-fix.md) 与本次 [架构源码核查](../Server/ARDY/runtime/scene-play-review-20260914-late/architecture-notes.md)。
