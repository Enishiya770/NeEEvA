# 多轮台词与 JSON 草稿验证（2026-09-09）

使用用户修改后的提示词完成 44 次真实本地模型生成。结论是：有效声明能传到 TTS，
但仍会出现正文混语、回复语种选择错误和不可靠的专名读法；JSON 草稿还存在截断问题。
本次新增的是验证工具，没有添加运行时词表替换、自动纠错调用或修改角色提示词。

## 测试范围

- 单轮对照：日语「了解。」、中文「了解。」、中文「听到哦。」接日语「了解。」、
  自我介绍、耳机/声场话题、英语短句，共 6 个场景，各 2 次。
- 保留日志历史：6 轮用户发言依次重放，每轮使用原日志中之前的模型回复，共 12 次。
  包含自我介绍、补充姓名、指出读音问题、要求继续用日语。
- 重新生成历史：同样的用户发言，但后续上下文使用本次新生成的回复，共 12 次。
  用户原本的纠正有时会与新回复不符，这是固定用户发言重放的局限。
- JSON 草稿：犹豫停顿、反馈姓名发音、明确要求日语、歌唱/说话边界，各 2 次。
  前三类使用日志中的转写片段；最后一类使用明确标记的合成声学证据，不冒充原录音。

模型调用使用本地 `antoneva`，关闭 thinking。正式回复沿用服务端默认采样，
评估上限 512 tokens；JSON 草稿使用场景实际配置的 128 tokens、temperature 0.2，
提示词直接提取自当前 C# 代码。两次使用 seed 73、74，每次调用前检查服务空闲。

这是对日志可见用户/助手文本的重建，**不是原始 HTTP 请求的精确重放**：没有记录的
动态记忆、技能目录和感知帧不伪造；第一轮问候的用户输入不可得，从首个带 ASR 计时的
用户轮次开始。记录了当前提示词与源日志的 SHA-256，以便辨认后续是否又有修改。

## 生成结果

| 检查层面 | 结果 | 含义 |
| --- | --- | --- |
| 36 次正式回复的声明 | 均输出有效语言声明 | 只证明声明格式和作用域可解析 |
| 12 次单轮对照的语种序列 | 12/12 符合预期 | 一次「了解」漏句号；一次名字写成「アンテナワ」 |
| 保留历史的 12 次回复 | 2 次 ja 正文夹中文姓名，1 次明确要求 ja 却回答 zh | 修改示例后仍可复现问题 |
| 重新生成历史的 12 次回复 | 未复现 ja 正文夹中文姓名 | 仍有语义误解和日语自然度问题，不能据此保证以后不混语 |
| 两种历史中明确要求日语的轮次 | 7/8 使用 ja | 第 8 次选择 zh，TTS 随之使用 zh |
| 8 次 JSON 草稿 | 6 次完整且正文与 ja 声明一致，2 次截断 | 两次姓名反馈场景均耗尽 128 tokens、finish_reason=length |

逐条检查正文发现以下有代表性的问题。没有用正则命中率代替日语质量验收：

- `logged_history/1/turn1`：`安托涅瓦として、いつでも話を聞くわ。` 位于 ja 语段。
- `logged_history/1/turn4`：`「安托涅瓦」って日本語の耳には…` 位于 ja 语段；
  即使正在讨论原文，引用也没有单独声明中文读法。
- `logged_history/1/turn5`：宣称「中央庭」读作「セントラルバレー」、
  「七日目」读作「なぬちめ」。这不是可以据以配置语音的可靠名称/读音资料。
- `controls/2/terminology`：把名字写成「アンテナワ」，并出现「新しい耳元」等不自然表达。
- `logged_history/2/turn5`：收到明确日语要求后仍输出整段中文、声明 zh。
- `logged_history/2/turn1` 和 `regenerated_history/2/turn1`：中文段落包含「ユウさん」，
  中文参数下这个日语称呼的实际读音仍需要单独听音检查。
- `regenerated_history/2/turn4`：把用户指出误读理解成“中文名更适合系统发声”，
  并生成了错误的记忆提议。测试未执行该工具，也未把它写进实际记忆。
- 两份 `name_feedback` 草稿均未形成完整 JSON；未完成正文已经出现中文姓名，
  其中一份还在 draft 内嵌入未正确转义的 `<lang>`。不能把它们计作成功切换语种。
- 两份歌唱边界草稿主要回应之前“漏了名字”的话题，未准确体现当前犹豫片段。
  这是上下文理解问题，不能由语言声明是否正确判断。

此前日志里的整句中文「嗯，我在听哦。不用着急，慢慢想。」被标成 ja 的情况，
本次两个犹豫草稿中**没有重现**。历史反例仍成立；两次未重现不足以判定修复。

## Unity 参数核对

为避免打断已打开的编辑器，用新编译的项目程序集在隔离 Unity 项目中运行。
正式回复经实际 `RoleOutputChannels`、`ChatSample.OnSpeechStreamDelta`、分句队列、
`GPTSoVITSFASTAPI.ResolveSpeech` 和请求构造方法；草稿经实际 JSON 解析器后核对字段。

44 个样本共检查 270 份完整 WAV/流式请求参数。声明未丢失、控制标签未进入发声文本，
「听到哦。」使用 zh、「了解。」按声明使用 ja 或 zh。两份截断草稿由实际解析器拒绝。
中文姓名混入 ja 的句子也按 ja 进入请求，说明文本质量问题会一路传递到合成端。

本次隔离运行只执行新样本检查，不计作重新通过全部既有 1476 项回归。
草稿的置信度门槛、长度裁剪、预合成调度没有在该检查中模拟。参数核对不发送 TTS HTTP。
初次隔离项目存在程序集命名/依赖问题；修正后最终运行退出码为 0。
日志中另有两个不参与本次检查的 VRM/UniGLTF 测试程序集加载告警。

## 复现与产物

```powershell
python -X utf8 Tools/check_speech_language_replay.py --runs 2
# Unity 非 Play 状态：Tools > NeEEvA > Inspect Generated Speech Replay
python -X utf8 Tools/check_speech_replay_audio.py
```

文件均在 `Logs/speech-language-check/`（本地评估数据，不提交日志中的个人对话）：

- `replay.json`：44 份完整请求、原文、有限规则检查结果、源对话和哈希。
- `replay-text-review.json`：逐条文本评估，与原始结果以哈希关联；不是人工听音记录。
- `replay-routing.json`：Unity 实际解析结果和 270 份 TTS 参数。
- `replay-unity-final.log`：最终隔离 Unity 运行日志。
- `audio/manifest.json` 和 WAV：6 份音频请求、时长与文件哈希。

下一步修复应分别处理正文语言一致性、用户指定语种的遵从和 JSON 草稿的完整性。
本轮验证没有把这些问题自动修复，也不能单凭清理示例或有效标签宣告完成。
