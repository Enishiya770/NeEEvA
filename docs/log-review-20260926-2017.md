## 2. 动作：真实成功与工程失败混在同一体验中

| 输入 | 实际情况 | 关键证据 |

| c10/c11/c13/c14 一直跟随 | 均误选停止跟随，纠正后仍同样选择，没有一条 follow 提交 | LF152587/155082/158245/160805及对应repair结果 |

`planContinuation` 是上轮新加的后继类型字段，但实际 OpenAICompatible Room 请求仅使用 `response_format:json_object`，完整 schema 放在提示文本中，未作为服务端受约束输出。这导致普通 approach 携带 follow 专用字段，执行端严格拒绝。必须让实际传输约束与 parser 统一，并在当前提供商上验证；不能用孤立 parser 测试通过代替线上生成链验证。

c8 的到达成功事实现在确实保留在最终回执中，但 `planRemaining` 仍整段复制角色原话，让程序认为还有尾目标，又耗一次约9秒规划，最后说“前一步完成，但后续未确认”。原子请求没有真实后继任务，这就是用户看到成功却觉得回复古怪的原因。应给有限任务明确终态，保留真正的复合目标，避免让重抄原话凭空创建下一步。

简单走近的快速分支另有接线缺口：`ChatSample.ActorIntent.cs:180` 要求 `TargetIsProgramBound`，生产代码只有字段定义和读取，没有赋值。因此即使 Actor 判为 approach/current_user/atomic，也继续走完整 Room。应由程序确认实际用户目标和绑定后使用短路径，不让模型自行赋予绑定权限。

## 3. 两种复读要分别修

跟随阶段的固定句不是用户表达不清。四轮 Fast 把“跟着我”选成 `stop_follow`，目标还是已结束的 approach ID。执行端正确拒绝，修复请求虽在上下文要求 `task_control=none`，却仍使用允许所有停止分支的 schema；四次修复再次输出 stop_follow。最后播放的是程序固定的“抱歉，我刚才没能组织好回答。可以换个说法吗？”及日文对应句。

因此应从实际任务状态生成合法控制集合：没有可停止任务时只有 none；有任务时仅列实际身份和合法类型；已否决停止后的修复不再开放该停止分支。保留执行端核验及真正的新目标，不能把错误字段事后清空冒充完成。

末尾是模型回复复读：c20 质疑架构和提示词，却重复 c15“准备好了，开始唱歌测试”；c23 已明确“测试到此为止”，仍重复 c19“别担心，交给我”。两轮都触发长文本重生成，多花约2.22/2.35秒，日志 `stillSimilar=true` 后仍公开。它不是音频播放器重新使用旧文件。

现有重复检测只是请求重新选择，没有要求恢复结果真正回答当前投诉/结束意图；Actor none 只能说明没有待执行动作，不能证明回答相关。另有字段名不一致：发送 `unpublishedDraft`，提示解释 `rejectedDraft`，应统一；日志不足以证明这是唯一复读原因。应使用当前输入、失败事实和必要历史作恢复，明确区分用户要求的复述与无关复读，不能简单禁止所有相似文本。
