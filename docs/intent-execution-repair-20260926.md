## 已实现的行为

### 角色草稿编译为有目标的任务

`ActorIntentProtocol` 升级为严格的 v3 表格，保留原有头部动作、等待、声明核验分支，新增 `task` 与 `target`。

- `other_action / replan / approach / current_user`：角色决定走近当前用户。
- `other_action / replan / follow / current_user`：角色决定持续跟随当前用户。
- 指定物体注视、其他实体、歌唱、组合或未知目标继续保留完整草稿交给完整规划器。
- 已完成动作的声明只进入核验，不通过补做动作来让旧声明成立。

这两个已知任务进入 `ChatSample.ActorTask.cs`，调用现有房间控制器，复用目标版本、导航、停止限制与任务来源检查。走近完成之后再跟随属于不同任务，不再仅因目标版本相同而被重复抑制。

受理后直接生成与草稿语言一致的简短事实回执。布尔受理结果不等于成功移动；同步导航失败、控制器未连接、停止限制和未受理分别给出对应回执。排队的回执在播放前再次核对动作、控制器和输出归属，停止、失败、替换或过期时撤销。

简单走近／跟随省去完整房间规划与后续说明、审核；复杂空间任务仍由原规划器定位目标，实际产生明确事实后可以使用简短回执。是否缩短真实首音时间仍需新 Unity 场景日志确认。

### 当前录音的时序和素材不会被短历史覆盖

`FastLoopPrompt` 和 `ChatSample.FastLoopContext` 保留有来源绑定的分段时序，包括段起止、识别文本、语言和模态信息。它们是观测证据，不是歌唱许可或自动选择的音频范围。

素材摘要最多保留六项，优先保留当前目标引用与独立的歌唱时序证据，再纳入最新录音。连续的纠错录音不会仅因“最新四条”截断而把前面的歌声证据挤掉。当前录音仍必须匹配真实 capture session 和完整最终转写；打字输入、自主轮次及同文不同录音不能借用旧录音。

普通历史中的角色台词与实际控制器事实分开。当前用户全文、结尾补充与当前任务事实优先。曾试验缩减 ActorIntent 事实表，但没有证明整体提速，且小范围回放出现不利判断，因此恢复原来的完整事实上下文，不将该精简方案部署。

### 补上 FastLoop 到录音歌唱决策的缺失路由

定位到的真实缺口是：FastLoop 已消耗本轮 FirstReply 的入口；交给房间规划后返回 `none`，续接默认 `recordingSinging=false`，正式流随即清除录音决策绑定并进入 General。因此“素材仍在”也不能保证进入来源／片段决策。

`ChatSample.FastLoopSkillRoute.cs` 在该交接点使用已有结构化 RoleDecision 做一次受约束的阶段选择。只有明确选择 `recording_singing` 才进入原有 `RecordingSingingDecision`；普通讨论、否定或其他工具目标继续原流程。路由本身不公开其生成台词，不选来源／范围，也不启动回唱。新轮次、取消和重复回调不能重启旧请求。

### 长回复重复的有限复核

仅把已实际完成播放的长台词作为重复参照。新草稿高度相似时，先请求一次包含当前输入和事实的重新判断，再走通常的意图与执行检查。单轮最多一次，用户主动要求引用或复述仍然允许。

这项机制是有界复核，不保证模型第二次一定改正。实测纠错对话中仍有错误解释、重新要求用户唱、以及重复旧道歉的情况，不能将“触发了复核”记为“理解已修好”。

隔离 Play 环境补齐了 VRM 编辑器导入依赖，并调用现有模型资产烘焙逻辑生成隔离参考姿态。此前初始化失败保留在原始日志中；没有修改生产姿态校验。最终报告为 `repair-regression-verified.json`、`actor-task-play-verified.json`，对应日志为 `unity-edit-verified.log`、`unity-play-with-restpose-verified.log`。源文件哈希保存在 `verified-source-hashes.json`。

这些检查不代替真实步行、远端动作生成、实际扬声器声音或回唱音质验收。测试输出中的合成片段和假模型只用于确定程序受理、权限和生命周期是否正确，不作为模型语义准确率或实际体验速度的证据。

## 下次场景验收关注点

1. 先走近，再持续跟随并继续普通对话：核对 `actor_task.submission`、控制器实际状态、任务是否重复或被对话取消。
2. 指定看台灯：核对完整目标规划是否定位到正确对象，不能只看分类为 replan。
3. 一段录音包含说明、歌声、结尾补充，随后纠正：核对原素材仍可见，`fast_loop.skill_route_resolved` 是否选择 RecordingSingingDecision，具体来源和范围是否通过后续决策。
4. 出错时纠正角色：分别记录当前输入是否被理解、是否还重复旧解释，以及动作事实与台词是否一致。
5. 用新的 `closed→首音` 日志比较整体延迟。模型小上下文请求耗时与程序避免了几次调用，均不能直接换算成实际场景首音提升。
