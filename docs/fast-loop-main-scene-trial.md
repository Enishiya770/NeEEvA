# FastLoop 主场景接入与真实服务试跑

日期：2026-09-25。用户授权把已验证的新路径接入主场景，验证真实语音起始、头部动作、打断和换意图。继续使用现有 Spark Qwen 与本机 GPT-SoVITS，没有部署模型或修改服务配置。

## 保存的改动

`Assets/Private/SailingMoon/Scenes/NeEEvA_SailingMoon_Day_Chat.unity` 仅新增三个序列化值：

```yaml
m_EnableFastTaskLoop: 1
m_EnableActorIntentCompiler: 1
m_EnableActorSpeechPreparation: 1
```

原本的 First Reply Routing 与 Qwen RoleDecision fast lane 已启用。与试跑前本地备份比较，除这三个值外场景内容一致。其他场景仍使用代码的 FastLoop 默认关闭值。

路由层现在显式接收编译器是否可用、头部动作集合和唯一支持的 `user_count_three` 条件。编译器可用时，角色可用普通自然语言提出即时头部意向或条件计划，由后续判断与运行时落实。编译器关闭时保留原纯对话/直接动作/旧规划器边界。采纳明确的单一即时头部请求时优先提交结构化 `head`，转到目标后自动保持。既有 gaze 的替换仍由实际控制器交接。

条件承诺应明确触发条件及之后要做的动作，不能只说等待过程。续等和回应计数不应凭旧用户请求重新推导另一个目标；明确重申同一计划继续保留计数。视觉目标、移动、唱歌、其他条件及复杂任务仍进入既有完整路径。

已登记条件任务会直接消费模型确认为单纯计数的输入：一、二只更新进度并安静结束本轮，三满足条件时执行原计划，不再额外请求普通角色回复。否则，角色可能自己接着数出“三”并提出提前动作。任务身份、修订号和输入序号仍逐一核验；带独立问题、目标修正的输入应判为 `none`，保留完整正常对话，明确取消走取消路径。这是事件归属修复，不依靠关键词直接驱动骨骼。

## 测量和隔离

入口是 `MainSceneFastLoopLiveRegression.RunBatch`，启动脚本：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File Tools/FastLoop/run-main-scene-trial.ps1
```

脚本用独立 Editor 子进程加载保存的主场景，启用真实图形、原角色、房间控制器、Qwen、TTS 和生产 `SendData()`/播放器。对话是自动提交的合成文本，用生产日志 `audio.formal_playback_advanced` 及 `AudioSource.timeSamples` 证明实际音频时间推进。播放器静音，不测物理扬声器听感、麦克风、ASR 或真实用户停话时间。

试跑仅在内存中关闭麦克风、自主发言、记忆读写、后台连续截图、开场 filler、字幕翻译/设置持久化、桌面字幕窗口及服务自启。MemoryHub 的独立对象在进入 Play 前关闭，避免 Awake 的 decay 写入与退出保存；角色眼睛、按轮视觉采集、房间与头部绑定保留。测试设置从不 SaveScene，退出后重新加载磁盘场景，并核验场景 SHA-256 没有变化。

Unity 子进程沿用项目已有的直连设置：`UNITY_PROXYSERVER` 显式存在且为空，不改系统代理。正常交互仍应使用项目根目录 `start_unity_direct_services.cmd` 启动。

当前结果写入 `Logs/fast-loop/main-scene-live.json`，完整日志为 `Logs/main-scene-fast-loop-live.log`。JSON 保留每轮草稿、真实判定、任务与控制器状态、计数进度、语音时延及诊断事件。试跑还从实际出站请求提取各判定阶段的 `current_user`，逐一核验与本轮提交文本完全一致；不保存请求凭据或完整角色系统提示。

## 调试中保留的失败证据

- `main-scene-live-first-failed.json`：普通语音成功，明确向右转头却走 reply→claim；真实完成事实不存在，运行时拒绝并改口，没有偷偷补做动作。随后明确了简单即时请求优先提交 head 的路由规则。
- `main-scene-live-wait-target-failed.json`：真实转头及动作中打断/换方向成功；首次等待草稿省略未来抬头目标，被判断为 head.hold；后续计数回应又被解释成新 head.raise 计划，导致计数被重置。随后补充了条件目标完整表达及续等语义。
- `main-scene-live-wait-meaning-failed.json`：计数已连续保留 1→2→3，并触发一次，但角色仍省略未来抬头目标，登记为 head.hold。该结果不能声称完成了用户所说的抬头。
- `main-scene-live-self-count-failed.json`：澄清后角色已明确确认“等你数到三，我再抬头”，登记为 head.raise。但系统处理“一、二”后又请求普通回复；角色自行接数“三”并提交即时动作，提前取消等待并抬头。随后修复单纯计数事件的归属，由现有等待任务直接消费，不再给该事件生成额外回复。
- `main-scene-live-release-failed.json`：计数事件修复后，前 11 轮工程场景通过，条件目标首次即确认为 head.raise，一、二安静等待，三后实际抬头。末轮要求解除保持却生成“好的，明白了。那就向右转吧。”，裁判判为 claim/head.right；实际不符合该完成声明，系统拒绝并改口，没有解除任务。整次结果仍为 failed。随后仅为试跑增加逐请求输入溯源，并保持生产协议不变复跑，区分输入串轮与模型选择/判定问题。

后续验收不改写这些历史记录。若模型再次遗漏目标，试跑会另记 `semanticDeviations` 并追加一轮明确目标的真实对话；只有角色实际确认的计划在条件后被执行，才计作工程链路通过。需要补问时报告为 `passed_with_semantic_clarification`，不能称一次理解全对。这符合用户已明确区分的“可接受语义偏差”与“自身意图未被执行”两类问题。

## 最终主场景试跑

最终 `main-scene-live.json` 状态为 `passed_with_semantic_clarification`，`executionPassed=true`。包含 13 轮（其中 1 轮是条件目标澄清），21 个真实判定请求的 `current_user` 全部与本轮提交文本相同。`savedSceneUnchangedDuringTrial=true`，`lateAudioRestarted=false`。保存场景的 SHA-256 为 `ABA05A02435B746F2404A93A9660DF841680E6890FE38EB3E7E217E7968BCB22`；与试跑前备份相比仍只有三个启用字段。

真实控制器验证通过：右转后保持、左转尚未到位时用户打断但独立头部任务继续、新的右转意向替换旧任务、计数一/二保留原任务与进度且不生成额外回复、三后才抬头并保持、实际音频开始后打断、随后解除头部保持。解除后任务为 cancelled，控制器 owner 为空、yaw/pitch 回到 0；没有旧语音重新启动。

模型语义质量须另读，工程通过不代表每轮意思都正确：

- 第一次等待草稿只说“在数到三之前，我会保持现在的姿势不动”，被登记为 head.hold。追加真实澄清后才明确 head.raise，随后按一→二→三执行。原偏差保留在 `semanticDeviations`。
- `interrupt-real-speech` 的普通日语叙述草稿被裁判误判为 replan，系统改为未执行提示。这轮只验证实际音频可以被打断，不能计作“三句描述成功交付”；其首音 7.14 秒也不是正常并行回复的代表值。
- 本次解除保持正确走 reply→cancel/head.release，前一次相同解除请求失败的报告仍保留。当前复跑排除了自身请求中的旧输入串轮，不能据此把前一次模型/语境偏差声称为已彻底消除。

## 真实播放时延与剩余问题

以下是最后一次试跑从提交文本到生产日志确认 AudioSource 时间样本开始推进，包含本轮场景采集、路由、判定与 TTS。全部播放器静音；不是从用户停止说话到扬声器可听的延迟，也不是 ASR 测试。

| 轮次 | 首音（秒） |
| --- | ---: |
| 开场日语 | 4.70 |
| 普通日语 | 3.92 |
| 普通中文 | 4.42 |
| 右转并保持的回执 | 4.54 |
| 打断后改为右转的回执 | 4.48 |
| 登记等待计划 | 4.49 |
| 澄清未来抬头目标 | 4.85 |
| 数到三、动作完成后的回执 | 3.68 |
| 普通叙述被误判后改口（随后打断） | 7.14 |
| 解除保持的回执 | 5.53 |

动作回执的首音不是动作启动时间；计数一/二按设计没有公开语音。

普通日语轮的日志时间线：约 1.38 秒获得角色草稿并发起 TTS，2.23 秒完成意图判断（判定本身约 0.85 秒），2.51 秒收到第一批 PCM，3.89 秒缓冲达标，3.92 秒 AudioSource 开始推进。证明判断与 TTS 已重叠，判断结束后仍有明显音频生成/缓冲等待。此前隔离试验的约 1.13 秒是“已有草稿→可用 PCM”，不能替代上述完整首音指标。

该轮首段请求的预缓冲为 1.20 秒。全次试跑有 12 条播放结束/中断记录，其中 5 段出现欠载，共 12 次；累计重新缓冲等待约 6.26 秒、插入静音约 1.54 秒。播放器的自适应预缓冲及实际 TTS 吞吐仍需单独优化；本次没有改动 TTS 服务配置，单次 GPU 读数不能证明硬件不足或确定竞争来源。

下一步宜先针对主场景下的 TTS 首段生成、缓冲和吞吐做专项测量与优化，再把同样的任务身份、执行回执、撤销和监督机制扩展至移动/唱歌。当前新路径仍是有限头部动作与单一条件的实验接入，不宣称移动和歌唱已经迁移到新框架。

后续 TTS 专项修复与对照结果见 [主场景 TTS 延迟记录](tts-main-scene-latency.md)。该专项使用固定文本隔离 TTS，并未重测本页的完整 Qwen 对话链路，因此本页的原始端到端时延仍按原测试解释。

## 回归

FastLoop 协议/运行时 48 个固定用例、275 项检查通过，新增能力集合边界及 reply 草稿不得直接改变运行时状态检查。FastLoop backend 33 项检查通过；ActorIntent 协议/来源/任务运行时 40 个固定用例、255 项检查通过，ActorIntent backend 51 项检查通过。Unity 真实 ChatSample 入口集成回归 68 个用例、445 项检查通过，覆盖单纯计数安静消费、插入真实提问后继续对话、重申计划保留计数、迟到/重复回调，以及原有任务与语音撤销边界。这些是确定性工程检查，不是模型语义正确率；集成回归的模型与音频使用可控替身，物理角色和真实服务由上述主场景试跑单独验证。
