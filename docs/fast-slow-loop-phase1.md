# 快慢框架第一阶段：独立头部任务与 Qwen 决策基线

日期：2026-09-25。范围是最小闭环，不是完整框架迁移。新路径由 `ChatSample.m_EnableFastTaskLoop` 控制，**默认关闭**。当前 Qwen 的语义测试未达到接管主场景的标准，默认运行仍走现有路径。受控测试显式打开实验开关。

2026-09-25 用户补充后的验收修正：本页 28/32 是对原先指定 route/candidate 标签的符合程度，不能作为新架构的主要成功指标。用户接受含糊停止的不同理解，也允许角色主动改变关注目标。主要目标是角色已经表达／采纳的意图能形成真实动作或持续计划，并如实反馈结果。后续实现已增加“角色输出草稿 → 快速意图判断 → 执行／条件任务”的头部动作切片，见 [意图与执行设计修订](fast-slow-loop-intent-execution.md)。下文保留第一阶段的原始测试结果，不追溯改写为新的闭环成绩；最新集成/物理报告使用同名输出文件，结果以该设计修订及当前报告为准。

## 已实现的闭环

用户最终输入 → 一次有界 Qwen JSON 决策 → 程序校验 → 持续头部任务／普通回复／停止声音／旧规划器交接。

在新路径中，按住说话、打字和实时语音通过同一个入口。模型不写 XML 标签，不生成任务 ID，不输出骨骼旋转。ASR/TTS、角色视野、现有头部控制器、身体移动和歌唱执行器沿用现有组件。歌唱、跟随、物体视觉、复合或条件任务仍交给现有规划器；这部分没有完成新架构迁移，也没有删除旧工具协议。

完整决策示例：

```json
{
  "version": 1,
  "route": "head",
  "candidate": "head.raise",
  "evidence": "请抬头",
  "speech": "",
  "language": "zh"
}
```

| 字段 | 第一阶段含义 |
| --- | --- |
| route | `reply` 普通回复；`head` 头部任务；`stop_voice` 只停止发声；`legacy` 交给已有规划器 |
| candidate | `head.raise/lower/left/right/hold/release` 或 `none` |
| evidence | 动作与停止声音必须引用当前用户输入中的连续原文，不能借用历史授权 |
| speech | 只有普通回复可以填纯文本；动作分支必须为空 |
| language | `zh/ja/en`，用于现有 TTS 的语言选择 |

上下抬头的单步预设为 12 度，左右为 18 度；程序按既有头颈限制约束目标，既有控制器逐帧平滑。`hold` 保持当前真实姿势。此任务只确认头部姿势，不能用它证明看清了某个物体。

## 所有权与取消

- `task.Id` 与对话轮次独立。方向修正保留 ID、增加 `Revision`；普通说话只推进输出版本，保留 starting/holding 任务。
- 物理控制权使用 `taskId:revision`。旧协程的结束处理不能释放新修订的控制权。
- 两秒物理租期由任务每 0.2 秒检查并续约。失去绑定、身体控制权冲突、闭眼、暂停或组件禁用会结束任务。租期不依赖模型持续发命令。
- 相同对话 generation 只能由一个新路径实例占有。只有明确交接时才让旧规划器接管，避免同时执行。
- 接受的用户输入立即写入历史，以对象身份交给旧路径；中途打断不会丢掉输入，相同文字的两轮也不会被合并。
- `stop_voice` 不取消头部任务；`head.release` 只释放匹配的头部控制权。范围含糊的停止应升级到旧规划器，现有 Qwen 对这一点仍有误判。

## 输出纠错的实际边界

动作完成台词来自执行回执，只有真实控制器 settled 且任务／修订／输出版本一致才能入队。待合成和待播的完成回执带有任务依赖；任务失败、修正、控制权丢失或输出撤销后，会通过现有语音队列取消机制移除对应 round。流式播放门也重新校验。

这实现了**依据执行事实撤销完成宣告**，并将原因交回后续上下文。它没有实现通用语义监督模型，不能保证识别任意普通台词中的知识错误，也不能撤回用户已经听见的声音。

## 验证与模型基线

可重复执行的测试位于 `Tools/FastLoop`。48 个具名案例包括 24 个开发语义例、8 个新增验证例、6 个非法协议例、10 个任务生命周期场景。确定性测试提供预设 decision，**不是模型识别准确率**。

- `run-regression.ps1`：编译生产协议、运行时和提示词工厂，48 个案例／270 项确定性断言。
- `transport/Run-Checks.ps1`：生产 Qwen backend 与传输替身的 33 项检查，包含完整返回验证、取消和历史交接。
- `FastLoopIntegrationRegression.RunBatch`：真实 ChatSample 调用入口、生命周期和语音队列门；受控 backend／controller 状态，不代表骨骼运动或实际声音。
- `FastLoopHeadPlayRegression.RunBatch`：在未保存的空 Play 场景加载实际 NeEEvA VRM，运行生产任务协程，验证真实转头、跨轮保持、续租、修正和释放。关闭模型、ASR、TTS 与服务自启。

本次 Unity 编译通过，最终集成测试 19 个场景／115 项检查通过（`Logs/fast-loop/integration.json`）。真实骨骼测试通过（`Logs/fast-loop/head-play.json`）：实际抬头约 11.05°，方向修正约 17.50°，跨轮保持与超过 3.2 秒的续租成功，明确取消后平滑回位，根位置与根旋转变化均为 0。该测试证明受控提案经真实执行器的闭环，不代表模型与 TTS 的完整对话验收。

真实模型运行保存在 `Logs/fast-loop/model-structured-context`：现有 `.175:8888` 的 `qwen3.6-35b-a3b`，32 条顺序请求，生产 prompt/schema，关闭 thinking，最大 256 输出 token。

| 指标 | 本次结果 |
| --- | --- |
| 协议合格 | 32 / 32 |
| route + candidate 符合预期 | 28 / 32 |
| 开发例 | 21 / 24 |
| 新增验证例 | 7 / 8 |
| 完整请求耗时 P50 / P95 | 1.079 / 1.955 秒 |

这是局域网中有界 JSON 请求耗时，包含本次网络／服务排队／推理；不是首 token 或首音延迟。没有做冷启动、并发压力、完整场景音频或长会话性能声明。8 个验证例很小，不能据此估计通用能力。

仍存在的原始路由偏差：一次明确向右转头被选为普通答复；含糊的“停一下”被选为只停声音；已有旧空间关注任务时仍提出新 head.hold；一个等待信号后转头的条件任务被当成普通答复。旧控制者的冲突已由运行时交接防护，但不能把这种防护算成模型分类正确。

初次联调还发现部署中的约束解码器未继承 `anyOf` 外层字段约束，漏掉 version/language；现在每个分支都声明完整闭合对象。原始失败证据保留在 `model-initial`，没有用宽松 parser 接受缺字段响应。

## 运行与后续验收

主场景 ChatSample 的 **Enable Fast Task Loop** 是实验开关；关闭即可恢复已有入口。启用后的受控手测顺序：抬头并保持 → 普通聊天 → 再抬高或转向 → 只停声音 → 解除头部保持。观察 `[FastLoop/Decision]`、`[FastLoop/Head]` 和 `fast_loop.speech_revoked`，区分模型提案与真实执行结果。

下一阶段应以这个接口和同一套案例比较判断后端，先测路由正确率、错误动作、误停／漏停和 p95，再决定是否部署或训练。需要补充会话／场景隔离的验证集和真实中文／日文表达，不能只对现有案例改提示词后宣布完成。当前基线不满足默认接管条件，所以此次没有启动新模型部署，也没有修改 Spark 服务或 ARDY 特征服务。
