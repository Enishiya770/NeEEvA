# 发声前校对与精简草稿实验

状态（2026-09-09）：按用户决定暂时搁置进一步校订方案，保存当前实现和实验记录。
逐句语言声明与 TTS 路由保留；独立校对和精简草稿不接入实时流程。
尚未验证出能满足本项目误改率、漏改率和延迟要求的替代模型，不将更换模型视为已成立的解决方案。

结论：**当前本地 `antoneva` 模型配合这组独立校对提示，不适合直接接入实时发声。**
增加一次调用未能可靠纠正混语，还引入了新的正文/语种不匹配。精简草稿改善了输出长度，
但存在空台词、控制标签和旧话题干扰，不能仅凭 JSON 完整就替换现有任务。

本轮完成 152 次本地生成：104 次校对、第一组 24 次草稿对照、第二组 24 次草稿补测。
只新增离线实验代码、实验提示和结果记录；没有给实时角色添加第二次调用。
既有逐句路由继续作为后续方案的基础。

## 实验设计

校对输入来自上次 Unity 核对保存的 42 份可解析正文（36 份正式回复、6 份 JSON 草稿），
另外加入 10 个明确标记为人工构造的边界用例。每个输入调用两次，共 104 次。
拒绝把之前两个截断 JSON 拼凑成可发声正文。

校对器使用独立任务提示，不携带整套角色行为提示。输入包括候选正文及其声明、最近用户
发言、最近四条可得对话、角色卡中已有的名称对应。只输出状态和 `{language,text}` 段落。
没有按词表替换正文。未知读法应返回 `needs_review`，不能把模型候选自己的断言当作依据。

校对使用 temperature 0、JSON schema、最多 768 tokens。两次 seed 不同，但低温下
50/52 个输入的两次输出完全相同，另外两组仅格式不同；不能将重复次数视为独立泛化证据。
测量的是**整份候选回复校对**，没有模拟实时每句等待、TTS 播放重叠或多任务争抢。

草稿以相同历史和输入比较：当前任务、精简任务、精简任务加 JSON schema。保留理解、
疑点、内心反应及模态字段，将台词/语种提前，限制内部短语长度。三种均使用原来的
128 token 上限和 temperature 0.2。补测换用 seed 91、92，并轮换三种方案的调用顺序。

## 校对结果：格式通过不等于可播放

104 次校对均形成有效 JSON，86 次自称 `unchanged`、18 次自称 `repaired`，
没有一次选择 `needs_review`。逐条文本评估发现：

| 场景 | 校对后的实际表现 |
| --- | --- |
| `安托涅瓦として、いつでも話を聞くわ。`，声明 ja | 两次均原样放行，未纠正中文姓名 |
| `耳机的声场は変わりますものね。`，声明 ja | 两次均原样放行，未纠正中文普通词 |
| 用户明确要求日语，但候选为整段中文 | 两次都保持 zh，未遵从用户语言要求 |
| 中文段落含日语称呼「ユウさん」 | 四次把声明从 zh 改为 ja，主体中文完全未翻译，新增更严重的误读条件 |
| 要求中文原名按中文读的日语解释 | 两次保留日语段里的中文姓名，又追加一段中文姓名；没有正确拆分，名字会重复 |
| 候选自己编造未知人名的官方读法 | 两次原样放行，未识别证据不足 |
| 候选编造「中央庭」「七日目」的读法 | 将原词也改成编造的读法，错误被保留并扩大 |
| 错拼名字「アンテナワ」 | 两次改回已有资料中的「アントネーワ」，但其他不自然表达未修好 |

6 个“原样保护”边界用例各重复两次：日语/中文「了解。」、自然中日切换、
既有汉字及品牌、否定与数字、正确日语名字。这 12 次均保留了预期正文和语种。
说明正常输入可以被保留，**但不足以证明错误输入能被纠正**。

另一个用例仅说“你可以用中文回应我”，候选为完整中文、误标 ja。校对器两次将全文
翻译成日语。它消除了正文/标签冲突，但不是期望的保留中文并修正标签；由于输入是
“允许中文”而非“必须中文”，这项不计作明确语言命令遵从率，只记录了不必要改写的倾向。

## 新增耗时

104 次校对的本地 HTTP 耗时中位数为 **0.456 秒**，P95 为 **0.731 秒**。
这包括输入处理和完整结果生成；若串行等待，会给该次发声增加等待。
当前没有证明能用播放重叠抵消它，也没有测繁忙服务时的排队时间。

因此目前不是“花约半秒即可解决混语”，而是“增加了约半秒，仍会漏错和误改”。
这组实验只说明当前模型/提示组合不足，不证明所有独立校对模型都无效。

## 草稿对照

第一组，每种方案 8 次：

| 方案 | 严格格式检查通过 | 通过结果中的空台词 | 输出 token 中位数 | HTTP 耗时中位数 |
| --- | --- | --- | --- | --- |
| 当前任务 | 7/8 | 0 | 106.5 | 0.829 秒 |
| 精简字段说明 | 7/8 | 5 | 53.5 | 0.528 秒 |
| 精简说明＋schema | 8/8 | 6 | 50.5 | 0.405 秒 |

当前任务一次被 128 token 上限截断；精简版一次额外输出了 `thought` 字段。
schema 约束了结构，却不能阻止模型把候选台词大量留空。其中两次用户明确要求日语，
schema 版本都没有准备可用开场，所以不能把空结果算作语言质量通过。

补测明确解释“候选台词不是立即发声，用户还在说话不构成自动置空理由”，每种 8 次：

| 方案 | 严格格式检查通过 | 通过结果中的空台词 | HTTP 耗时中位数 |
| --- | --- | --- | --- |
| 当前任务 | 4/8 | 0 | 0.845 秒 |
| 澄清后的精简说明 | 4/8 | 0 | 0.507 秒 |
| 澄清后的精简说明＋schema | 6/8 | 0 | 0.465 秒 |

补测中当前任务四次截断。精简版四次不通过：两次正文含 `<silent/>`，两次缺字段。
schema 补齐了字段，但两次 `<silent/>` 仍可出现在字符串值里，必须由独立的格式检查拒绝。
两份歌唱边界草稿仍围绕上一轮姓名话题作答，没有正确把握当前犹豫片段。
“名字はアントネーワよ”也把名字/姓名表达混淆，虽有日语文字，不等于语义自然。

这些格式检查是**实验端的严格规则**，包括字段、类型、正常结束和禁止控制标签，
不是宣称生产解析器已经改成同样规则。现有程序对部分格式更宽松。
schema 的字符串长度约束也可能把内部短语压成不自然片段，需要检查信息损失。

性能比较受到缓存影响：第一组总是按当前→精简→schema调用；补测轮换了顺序，
但每组只有 8 个样本，且当前任务首次处理较长上下文耗时 2.746 秒。
不能把这些中位数当作严格控制缓存后的因果加速比例。

## 接入判断

- 当前校对提示不接入实时播放。标签与 JSON 正确不是放行正文的充分条件。
- 当前精简草稿候选也不直接替换生产任务。输出更短的方向有价值，
  但空台词、控制标记与语义损失尚未解决。
- 下一轮若继续验证，应优先比较一个具备稳定中日文校订能力的独立模型，
  使用本轮固定失败集以及未参与提示调整的新样本；先测纠错和误改，再测实时延迟。
- 结构约束、缺字段/截断检查可以作为独立的工程防护，但不能包装成混语修复。
  未知读法必须能承认信息不足，不能只从一个模型转交给同一个模型便视为已核实。

## 代码和证据

```powershell
python -X utf8 Tools/test_speech_review_experiment.py
python -X utf8 Tools/check_speech_review_experiment.py --suite all --runs 2
python -X utf8 Tools/check_speech_review_experiment.py --suite drafts --runs 2 --seed-start 91 --counterbalance --compact-prompt Tools/speech_review_experiment/draft_compact_candidate.txt --output Logs/speech-language-check/review-draft-followup.json
```

工具每次请求前检查本地模型服务空闲；返回的工具标签不执行，不写角色历史或记忆。
校对与草稿实验均未发送 TTS 请求或播放音频。

本地证据在 `Logs/speech-language-check/`：

- `review-experiment.json`：第一组 128 次请求/响应、时间、tokens、输入哈希与格式结果。
- `review-draft-followup.json`：补测 24 次请求/响应，包含调用顺序和新种子。
- `review-experiment-text-review.json`：逐条文本评估，与两份原始结果以哈希关联。

新增 4 个无网络边界测试通过，覆盖共享汉字及切换、截断/非法输出拒绝、空草稿保留模态，
以及明确验证“结构检查不会冒充语义检查”。运行时 C# 和角色提示词在本轮未改动。
