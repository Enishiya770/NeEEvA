# 主场景 TTS 延迟与流式播放记录

更新日期：2026-09-25。本文记录本轮已完成的修复、局部基准、最终复测和回退方法。

**最终复测：在四次固定短句中，客户端修复加 `cpu_threads=1` 将首次 AudioSource 推进均值从 2.122 秒降至 1.909 秒，再缓冲总等待从 2.463 秒降至 0.577 秒，完成播放回调均值从 5.733 秒降至 4.925 秒。仍有一次普通短句实际暂停补缓冲，另两次有欠载补零，不能称为完全无卡顿。**

中途版本曾出现“更早开始播放，但再缓冲反而更长”的退步，本文保留该历史对照。最终修改按照 DSP 时间线上的实际缺口位置延迟暂停，避免过早暂停已经排队的真实音频；这些结果仍限于 TTS 局部和静音 AudioSource 进度，不代表物理首音或 LLM 全链路延迟。

## 已完成的修改

生产客户端位于 [GPTSoVITSFASTAPI.cs](../Assets/AIChatTookit/Scripts/TTS&&STT/GPT-SoVITS/GPTSoVITSFASTAPI.cs)。本轮修改针对 PCM 接收和播放边界：

- 音频回调请求的数据大于已到达 PCM 时，先按顺序消费现有 PCM，只对缺少的部分补零。此前会保留不足一整次回调的数据，并给整次回调填静音。
- 下载完成回调及时标记输入结束。正常句尾用于填满音频回调的零，不再算成网络欠载，也不再因此增加下一句的自适应预缓冲。
- WAV 头和首批 PCM 到达事件在音频队列锁外通知，避免在锁内进行日志等额外工作。
- 记录首批 PCM、预缓冲就绪、播放许可等待、创建 AudioClip、调用 `AudioSource.Play()` 等时点，区分合成、缓冲和播放阶段。
- 欠载发生时记录 DSP 时间线上首次缺口的位置，让已经排队的真实 PCM 继续播放，到接近缺口时再暂停补缓冲；增加再缓冲次数、等待时长、最大回调采样数等观测字段。完成播放仍等待 AudioSource 追上真实 PCM 的结束位置。

这些是数据处理及观测层面的修复，不能单独保证持续生成速度高于播放速度，也没有消除本轮真实场景中观察到的再缓冲。

服务总控 [neeeva_services.ps1](../Tools/neeeva_services.ps1) 新增 TTS 专用 CPU 线程配置：

1. 只在 `start` / `restart` 且选中 `tts` 时解析配置，并在重启停止现有服务之前验证。
2. 非空环境变量 `NEEEVA_TTS_CPU_THREADS` 优先于可选文件 `Server/RuntimeLogs/tts_runtime.json` 的 `cpu_threads`。范围为整数 `1..32`；JSON 字段须为整数，不能用字符串、布尔值、空值或小数。
3. 仅在启动 TTS 子进程时设置 `OMP_NUM_THREADS` 和 `MKL_NUM_THREADS`；无配置时保留原继承环境。启动成功或失败后都恢复控制脚本的原环境，包括原先不存在的变量；不修改用户级、系统级环境，也不把该覆盖应用于 ASR。
4. 启动输出显示选用的线程数及来源，便于核对实际生效路径。

PowerShell 5.1 与 PowerShell 7.6.5 均完成了无服务副作用的函数抽取及启动模拟验证，各 39 项断言通过，覆盖优先级、非法值、适用范围、启动失败恢复、空变量恢复和重启前验证顺序。这些模拟验证不替代实际服务启动验收。

## 当前本机运行配置与回退

本机已写入以下运行配置，并由总控执行过仅 TTS 重启：

```json
{
  "cpu_threads": 1
}
```

文件为 `Server/RuntimeLogs/tts_runtime.json`，属于本机运行配置目录。写入本记录时，主任务记录的 9880 进程 PID 为 `12516`；PID 只用于本次操作追踪，后续重启会改变它。`cpu_threads=1` 控制 CPU 算子线程，不表示把 CUDA 合成迁回 CPU，也没有在本轮切换模型或数值精度。

回退线程设置时：

1. 移除 JSON 中的 `cpu_threads` 字段（保留有效 JSON 对象），或暂时移走该可选配置文件。
2. 若启动终端设置过 `NEEEVA_TTS_CPU_THREADS`，同时在该启动环境中取消它，否则它仍会覆盖文件。不要把字段改成 `0`；`0` 是非法值。
3. 在已经配置好现有 GPT-SoVITS 安装路径的终端中，从项目根目录执行：

   ```powershell
   .\Tools\neeeva_services.ps1 restart -Only tts
   ```

此操作只重启 9880 TTS。没有显式线程配置后，服务恢复继承启动终端的 `OMP_NUM_THREADS` / `MKL_NUM_THREADS`；如果终端原本已有这两个变量，它们仍会生效，并不保证等同于第三方库的无环境变量默认值。不要为回退 TTS 而停止其他服务。

客户端代码回退应只回退本轮 PCM/播放修改，并重新运行 PCM 及主场景测试。该生产文件还包含此前的语言和对话功能修改，不宜整文件覆盖为旧版本。

## 测试范围与指标含义

主场景测试加载 `Assets/Private/SailingMoon/Scenes/NeEEvA_SailingMoon_Day_Chat.unity`，使用真实场景渲染、生产 GPT-SoVITS 客户端和 AudioSource。测试中的隔离只存在于内存，不保存场景或质量设置；不使用 Qwen、ASR、麦克风，也不写用户记忆。

每份主场景报告用于性能统计的是 **4 次短句样本**：中文和日文各两次。它们是两条固定文本的重复测量，不是四个不同文本，也不是覆盖长句或复杂韵律的语料集：

- 中文：`今天辛苦了，先休息一下吧。`
- 日文：`今日も一日、よく頑張ったね。`

另有播放途中取消与取消后的新播放用例，它们不计入这四句统计。各次运行的场景启动等待单独记录并排除出统计；它不是模型冷启动延迟的完整测量。

所有 AudioSource 均静音。`firstAudioSourceAdvanceSeconds` 表示观测到 `timeSamples` 首次推进，**不等于扬声器/耳机实际首音，也不包含声音传播、设备延迟或人工听感判断**。本文也不测量从用户说话、ASR 结束、LLM 生成、意向判断到角色开口的完整链路。

指标解释：

- 首批 PCM：TTS 请求开始至客户端收到第一批可解析音频数据。
- 首次播放推进：TTS 请求开始至 AudioSource 采样位置首次推进。
- 再缓冲等待：一次句子播放过程中，为继续积累 PCM 而暂停等待的累计时间。
- 欠载补零：输入尚未结束时，音频回调因数据不足而填入的零采样时长。它与暂停等待是不同观测量，不应简单相加当作人工可闻停顿。
- HTTP RTF：该次 HTTP 完成耗时 / 生成音频时长；小于 1 表示整个请求的平均生成与传输速度快于音频时长，但不保证每个局部片段都及时到达。表中 RTF 是四次单独 RTF 的算术平均。

样本只有四次，表内最大值仅描述这四次观测。原报告提供的 P95 在这四次样本上等于最大值，不应解释为可靠的总体第 95 百分位。

## 已有主场景基准

单位为秒，数值保留三位小数。首批 PCM 为均值；首次播放推进同时列中位数与最大值；再缓冲及补零为每句均值。

| 运行 | 首批 PCM 均值 | 首次播放推进中位数 | 首次播放推进最大值 | 再缓冲等待均值 | 欠载补零均值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| [原客户端，默认帧设置](../Logs/tts-latency/baseline-default.json) | 0.907 | 2.068 | 2.621 | 0.616 | 0.196 |
| [原客户端，临时限制 60 FPS](../Logs/tts-latency/baseline-fps60.json) | 1.047 | 2.155 | 2.497 | 0.571 | 0.168 |
| [新客户端，原线程环境](../Logs/tts-latency/after-client-default.json) | 1.103 | 2.019 | 2.310 | 1.104 | 0.313 |
| [新客户端，CPU threads=1](../Logs/tts-latency/after-client-threads1.json) | 0.954 | 1.728 | 2.158 | 0.929 | 0.268 |
| [最终客户端，CPU threads=1](../Logs/tts-latency/final-client-threads1.json) | 0.949 | 1.810 | 2.515 | 0.144 | 0.135 |

默认帧设置为 `vSyncCount=1`、`targetFrameRate=-1`。60 FPS 对照仅在内存中改成 `vSyncCount=0`、`targetFrameRate=60`，没有显示稳定降低首段等待的证据，未作为持久化优化。音频配置保持 48 kHz 输出、DSP buffer length 1024、buffer count 4，`Time.timeScale=1`。

中途“新客户端加单线程”的首次推进中位数较原始默认基线缩短约 0.340 秒，但平均再缓冲由 0.616 增至 0.929 秒；四次普通短句仍分别记录一次再缓冲。相对“新客户端、原线程环境”，单线程的首段和再缓冲均有改善，但当时仍不足以说明整体播放优于原始基线。最终客户端的首段中位数并非这几次运行中最小，不过再缓冲等待已明显减少，详见最终验证。

预缓冲在同一次测试内会根据前句稳定性自适应变化；不同运行也有生成音频长度差异。这些数字是实际端到端 TTS 样本结果，不能视作严格隔离了单个参数的性能因果实验。尤其不能把原始基线至新客户端单线程的差值全部归为线程设置收益，因为客户端何时开始播放的策略也发生了变化。客户端修改还改变了欠载处理和统计边界，因此欠载次数本身尤其不适合跨版本直接等同比较。

表中前四份报告形成于最后一轮“按实际 PCM 缺口位置延迟暂停”的修改之前，最后一行为该修改后的真实主场景复测。历史结果不能替代最终版本验收，也不应从小样本推断未测试场景的稳定性。

上述五份报告的执行状态均为 `passed`，取消用例均按请求取消，随后新播放成功，`lateAudioRestarted=false`，退出后场景与质量设置校验均未改变。这里的 `passed` 表示夹具功能断言通过，不表示没有卡顿或延迟问题。

## 本机 HTTP 合成对照

这些请求绕过 Unity 与 AudioSource，只测本机 9880 HTTP 流。每份报告剔除 `warmup` 后统计四次普通短句。参数未记录的列保留为“未记录”，不从文件名之外推测精确运行值。

| 报告 | CPU 线程条件 | 流模式 / 最小 chunk | seed / split | 首批 PCM 均值（秒） | 完成均值（秒） | 平均 RTF |
| --- | --- | --- | --- | ---: | ---: | ---: |
| [HTTP 基线 chunk12](../Logs/tts-latency/http-baseline-chunk12.json) | 原继承环境 | 3 / 12 | 42 / 未记录 | 0.547 | 2.669 | 0.974 |
| [HTTP chunk24](../Logs/tts-latency/http-chunk24.json) | 原继承环境 | 3 / 24 | 42 / 未记录 | 1.008 | 2.697 | 0.994 |
| [threads1 默认 seed](../Logs/tts-latency/http-threads1-defaultseed.json) | 1 | 3 / 12 | -1 / 未记录 | 0.383 | 2.068 | 0.744 |
| [threads1 cut0](../Logs/tts-latency/http-threads1-cut0.json) | 1 | 3 / 12 | 42 / cut0 | 0.545 | 2.893 | 1.058 |

chunk24 对照没有改善这些样本的首批 PCM；mode2 的整体 RTF 较低，但首批 PCM 比单线程 mode3 默认 seed 更慢。这些试验的 seed、分句或流模式不完全一致，生成音频时长也不同，不据此直接推广模式排名或归因全部收益。不能把 HTTP RTF 当作主场景无再缓冲保证；真实渲染与音频消费同时运行时的差异仍需继续定位。

| 诊断请求 | 首批 PCM（秒） | 响应完成（秒） | 音频时长（秒） | RTF |
| --- | ---: | ---: | ---: | ---: |

在真实场景渲染期间，替换传输调用后仍出现明显变慢，因而现有证据不支持“仅更换 UnityWebRequest 就能解决主瓶颈”。这两次诊断也不能单独确定 CPU、GPU、驱动调度或服务端竞争各占多少；它们只说明差异不局限于 UnityWebRequest 或 AudioSource 消费路径。仍需把场景运行条件与服务合成侧一起调查。

## PCM 确定性回归

[pcm-regression.json](../Logs/tts-latency/pcm-regression.json) 最新记录 9 个用例、181 项检查通过，失败用例为 0。测试通过反射使用生产 `PcmStreamingDownloadHandler`，输入确定性生成的 PCM16 WAV 字节并模拟音频读取，覆盖：

- 分段 WAV 头和奇数字节边界。
- 不足一个回调长度时保留正确音频顺序，并在后续数据到达后恢复。
- 连续欠载信号只被消费一次。
- 首次缺口位置与消费后的重置、位于第零采样的缺口在 EOF 后仍正确保留，以及立体声缺口按交错采样索引计算。
- 短 WAV 的正常 EOF 尾部不计为欠载。
- 长 WAV 跨下载和读取边界，以及立体声交错和时长计算。

此回归没有网络请求、AudioSource、真实 DSP 调度或扬声器测试，主要证明 PCM 处理边界正确，不能证明真实运行性能。

## 最终验证

持久化 `cpu_threads=1` 并通过总控重启后，最终生产客户端完成 [final-client-threads1.json](../Logs/tts-latency/final-client-threads1.json) 的真实主场景复测。运行使用默认场景帧设置，报告为 `passed`，退出前后场景与质量设置哈希均未改变。

以下只比较四次普通短句，单位为秒：

| 指标 | 原始默认基线 | 最终客户端 + threads1 |
| --- | ---: | ---: |
| 首次 AudioSource 推进均值 | 2.122 | 1.909 |
| 首次 AudioSource 推进中位数 | 2.068 | 1.810 |
| 请求开始至完成播放回调均值 | 5.733 | 4.925 |
| 四句再缓冲总等待 | 2.463 | 0.577 |
| 四句欠载补零总时长 | 0.784 | 0.539 |

最终四句中，`zh-2` 发生一次 0.577 秒的真实暂停；`zh-1`、`ja-1` 没有暂停，但仍分别存在约 0.125 秒和 0.074 秒的欠载补零。`ja-2` 未记录暂停或欠载补零。因此本轮结果支持保留当前修复与线程配置，不能解释为所有片段已经连续无缺口。

取消用例正确终止旧流；取消后的新句成功播放，首次 AudioSource 推进为 2.151 秒，另有 0.311 秒再缓冲等待。普通短句和取消后新句合计发生两次实际暂停，其暂停位置断言均通过。`lateAudioRestarted=false`，未观察到旧流晚到后重新启动播放。这些是本次夹具范围内的取消与恢复证据，不替代完整对话中所有打断、换意图场景的测试。

本轮保留客户端 PCM/暂停边界修复和 TTS 专用单线程配置。仍需注意真实场景渲染时服务吞吐比场景外 HTTP 更慢、长句尚未纳入本组基准、存在残余暂停与补零，以及静音进度不能验证实际听感。后续改动应同时复测首次推进、完整播放时间、再缓冲和取消恢复，避免只优化开头而增加中途等待。
